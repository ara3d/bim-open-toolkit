# IfcOpenShell: comparison and integration brainstorm

> Brainstorm, 2026-10-11. An honest comparison of BIM Open Toolkit with IfcOpenShell (https://github.com/IfcOpenShell/IfcOpenShell), the most used open-source IFC project, followed by a wide, unjudged list of integration ideas, the tensions, five grouped approaches, and a soft recommendation. IfcOpenShell is not a node editor like ifc-flow or IFClite (`docs/proposals/ifc-flow-ifc-lite-brainstorm.md`); it is the library, toolchain, and authoring application that most open IFC work in the industry stands on, so the comparison matters as much as the ideas. Nothing here is decided; the next step is to pick ideas and evaluate them (the `platonic:investigate` skill for a spike, `platonic:no-new-wheels` for reuse). Facts about IfcOpenShell were checked on 2026-10-11 against the repository at its default branch `v0.9.0` (README, the recursive file tree from the GitHub API, `docs/ifcconvert/usage.rst`, `docs/ifcmcp.rst`, `docs/ifcopenshell-js/*.rst`, and source files named below), the GitHub REST API, pypi.org and pypistats.org, the npm registry, extensions.blender.org, bonsaibim.org, academy.ifcopenshell.org, and community.osarch.org; they are marked **docs**. Facts about the toolkit come from this repository and are marked **docs** too. Everything else is **inferred**. Two sources were weak and say so where used: a LinkedIn repost of the Bonsai 0.9.0 announcement, and third-party MCP directory listings.
>
> Earlier work in this repository: `docs/proposals/ids-reuse.md` (2026-09-27) settled that the toolkit's IDS (Information Delivery Specification) evaluator is built over BOS tables, with IfcOpenShell's `ifctester` (LGPL-3.0) as an external parity reference driven by `tests/data/Ara3D.Ids.Tests/parity/run-ifctester.py` in bim-open-data; `docs/proposals/buildingsmart-integration-brainstorm.md` (2026-10-10) covers IDS, the validation service (whose rules run on IfcOpenShell), bSDD, and BCF, and is referenced here rather than repeated. `docs/CONTRIBUTIONS.md` has one shared row, "IfcOpenShell, xBIM, web-ifc (That Open Company)", which says they are "used or comparable at the parsing layer" and that the toolkit adds "the table schema, the graph, run records, and byte-exact partial writes". `docs/nrc-walkthrough.md` does not mention IfcOpenShell; `docs/proposals/nrc-deliverables.md` lists "runs in Bonsai" as a manual test in the paper repository; `docs/proposals/snowdon-federation.md` cites `ifcpatch` MergeProjects. bim-open-flow's README compares the editor with IfcSverchok.

## What IfcOpenShell is, in the terms this repository uses

- **The project.** A C++ IFC parser and geometry engine with Python bindings, started in 2011 (README of `ifcopenshell-js`) and on GitHub since 2015-08-10, plus about twenty tools in one repository. **docs** The README lists `bcf`, `bonsai`, `bsdd`, `ifc2ca`, `ifc4d`, `ifc5d`, `ifccityjson`, `ifcclash`, `ifcconvert`, `ifccsv`, `ifcdiff`, `ifcedit`, `ifcfm`, `ifcmcp`, `ifcopenshell-python`, `ifcpatch`, `ifcquery`, `ifcsverchok`, and `ifctester`, each with its own licence and package. **docs** Version 0.9.0 of the Python packages reached PyPI on 2026-09-29; the default branch is `v0.9.0`. **docs** The Bonsai announcement calls 0.9 "the big IfcOpenShell refactoring" and claims models open "around three times faster" with "less than half the additional RAM". **docs** (LinkedIn repost only; the official notes were not found)
- **Schemas and parsing.** "Complete parsing support" for IFC2X3 TC1, IFC4 ADD2 TC1, IFC4X1, IFC4X2, and IFC4X3 ADD2; "extensive geometric support" for IFC2X3 and IFC4; other EXPRESS schemas can be loaded at run time from Python. **docs** (README) No IFC5 or IFCX reader was found in the tree. **inferred**
- **The Python API.** `ifcopenshell.open(path)` returns a `file`; `model.by_type("IfcWall")` returns entity instances whose attributes read as Python properties; `ifcopenshell.util.element.get_psets(element)` returns property sets as dictionaries; `ifcopenshell.util.selector.filter_elements(model, "IfcWall, IfcSlab")` runs the selector query language (classes, attributes, property filters, and a value-formatting grammar in `util/selector.py`). **docs** `ifcopenshell.util` has about 30 modules (`element`, `pset`, `unit`, `placement`, `shape`, `cost`, `sequence`, `classification`, `geolocation`, `alignment`, and others). **docs**
- **The write API.** `ifcopenshell.api` holds 384 functions in 35 modules (`root`, `pset`, `spatial`, `geometry`, `material`, `classification`, `cost`, `sequence`, `alignment`, `georeference`, `drawing`, and more), each a typed Python function such as `ifcopenshell.api.pset.edit_pset(model, pset=..., properties={...})`; the older `ifcopenshell.api.run("pset.edit_pset", ...)` form is marked deprecated in the 0.9.0 source. **docs** (counted from the file tree; `api/__init__.py`) Pre- and post-listeners can be attached to any API call. **docs** `file.write(path)` serialises the whole in-memory model; nothing in the documentation describes a partial write that leaves untouched bytes identical. **inferred**
- **Geometry.** `ifcopenshell.geom.iterator(settings, model, cpu_count)` meshes a model on several cores with caching and reuse of shared representations. **docs** Kernels are plugins under `src/ifcgeom/kernels/`: `opencascade` (IfcConvert's default), `cgal`, `cgal-simple`, the hybrid `hybrid-cgal-simple-opencascade`, `manifold` (new in the 0.9 line), and `passthrough`. **docs** No published timing table was found. **inferred** (searched 2026-10-11)
- **IfcConvert.** A command-line converter: `.obj`, `.dae`, `.glb`, `.stp`, `.igs`, `.xml` and `.json` (property definitions and decomposition tree, the JSON in xeokit's format), `.rdb` (RocksDB), `.svg` (2D floor plans), `.ttl` (RDF Turtle with WKT geometry), and `.ifc`; `-j` sets the thread count, `--kernel` the geometry kernel. **docs** (`docs/ifcconvert/usage.rst`) The serialiser folder also holds a USD writer. **docs** (`src/serializers/usd_serializer.cpp`)
- **SQL.** The `ifcpatch` recipe `Ifc2Sql` writes SQLite or MySQL, one table per non-abstract IFC class, with options for inverses, property sets, and geometry (`should_get_psets`, `should_get_geometry`); `ExtractPropertiesToSQLite` writes properties only. `ifcopenshell.sql` opens such a SQLite database as an IfcOpenShell `file`, so the same API runs over it. **docs** There is no DuckDB, Parquet, or dataframe export in the tree. **inferred** (searched the file tree) `ifcpatch` has 38 recipes, among them `MergeProjects`, `SplitByBuildingStorey`, `ExtractElements`, `Optimise`, `ResetAbsoluteCoordinates`, and `Migrate` (schema conversion). **docs**
- **Tools around the library.** `ifctester` reads, writes, and audits IDS, with reporters `Console`, `Txt`, `Json`, `Html`, `Ods`, `OdsSummary`, `Bcf`, and `Sqlite`, and a browser authoring app (Svelte over Pyodide) at ifctester.org. **docs** (`ifctester/reporter.py`, `ifctester/webapp/`) `ifcclash` checks intersections, collisions, and clearances; `ifcdiff` writes the differences between two models as JSON; `ifccsv` exports and imports schedules; `ifc4d` converts to and from project-management schedules; `ifc5d` does quantity take-off and cost; `ifcfm` extracts facility-management handover data; `bcf` reads and writes BCF-XML and talks to BCF-API; `bsdd` queries bSDD. **docs**
- **Bonsai.** The Blender add-on formerly called BlenderBIM: native IFC authoring, where Blender edits the IFC model directly instead of converting to it. GPL-3.0-or-later. **docs** Version 0.9.0 on Blender Extensions needs Blender 5.1 or newer; the listing counts 156,119 downloads. **docs** bonsaibim.org now names three applications: Bonsai Studio (the add-on), Bonsai Viewer (a C++ and Qt desktop viewer, `src/bonsaiviewer/`), and Bonsai Web, "coming soon". **docs** Daily unstable builds are tagged on GitHub (eight on 2026-10-10 alone). **docs** `ifcsverchok` is a node add-on for Blender, also GPL-3.0. **docs**
- **The web and WASM builds.** Two routes exist. Pyodide wheels from `IfcOpenShell/wasm-wheels` run the full Python package in a browser, with a demo at wasm.ifcopenshell.org; its own documentation calls it "incredibly heavy". **docs** New in the 0.9 line, a native WASM build with TypeScript bindings: npm `ifcopenshell` 0.9.0 (published 2026-10-07) and `@ifcopenshell/wasm` 0.9.0 (2026-10-10), loaded as plugins per schema, geometry mapping, and kernel (`runtime.loadPlugin('kernel', 'manifold')`), with a three.js example; the installation page still reads "Installation from npm: TODO". **docs** ifc-flow runs the Pyodide route. **docs** (the ifc-flow brainstorm)
- **AI.** The project ships its own MCP (Model Context Protocol) server: PyPI `ifcopenshell-mcp`, first released as 0.8.5 on 2026-04-01, 0.9.0 on 2026-09-29, written by five core developers across 18 commits. **docs** It holds one model in memory and exposes 25 tools: session (`ifc_new`, `ifc_load`, `ifc_save`, `ifc_reset`), query (`ifc_summary`, `ifc_tree`, `ifc_info`, `ifc_select` with selector syntax, `ifc_relations`, `ifc_contexts`, `ifc_materials`, `ifc_schema`, `ifc_schedule`, `ifc_cost`), checks (`ifc_validate`, `ifc_clash`), `ifc_quantify` (writes base quantities through `ifc5d` into the model in memory), pictures (`ifc_plot` returns a 2D drawing and `ifc_render` a 3D view, both as inline PNG images the model can look at), shape building (`ifc_shape_list`, `ifc_shape_docs`, `ifc_shape`), and editing (`ifc_list` and `ifc_docs` to discover API functions, `ifc_edit` to call any of the 384). **docs** (`src/ifcmcp/ifcmcp/server.py`, PyPI description) Edits stay in memory until `ifc_save`; there is no dry-run or diff tool. **docs** It wraps two command-line tools, `ifcquery` (JSON queries) and `ifcedit` (API calls from the shell). **docs** `src/ifcchat` is a browser assistant on the same code, at ai-chat.ifcopenshell.org, that runs in Pyodide with the user's own OpenAI, Anthropic, Gemini, or OpenRouter key. **docs** Several of these documents begin "This file was generated with the assistance of an AI coding tool". **docs** Outside the project: `Bonsai_mcp` (JotaDeRodriguez, a fork of BlenderMCP) and `bonsai-mcp` drive a running Bonsai session; the MCP4IFC paper (arXiv 2511.05533, University of Rostock and TU Clausthal) reports an LLM building and editing IFC through Bonsai with tools plus retrieval-augmented code generation; Impertio's MIT skill package for Blender, Bonsai, IfcOpenShell, and Sverchok has 73 skills (`docs/proposals/openaec-foundation-integration-brainstorm.md`). **docs** (directory listings and the arXiv abstract)
- **Community and teaching.** The OSArch (Open Source Architecture) forum, launched 2020-02-04, shows about 3,300 discussions. **docs** IfcOpenShell Academy (academy.ifcopenshell.org) is a blog of tutorials whose newest post on the front page is from 2021. **docs** Courses outside the project use the library: IFC-101 (ten free episodes), aeco.dev, and RWTH Aachen's notebooks. **docs** Funding is by donation through Open Collective. **docs**

Read plainly: IfcOpenShell is the industry's open IFC engine and the toolkit is not a competitor to it in that role. On parsing breadth, geometry, authoring, standards support, and community, IfcOpenShell is ahead by a margin no plan here closes. Where the two meet head on is Claude. `ifcopenshell-mcp` puts IfcOpenShell inside Claude Code with one `pip install`, and it can do what `bimopen-ifc` cannot: edit, validate, clash, quantify, and return a picture. The toolkit's distinct claims are the ones IfcOpenShell does not make: an analysis is a graph over tables whose run replays from content hashes; a person who writes no code gets the same graph Claude built; write-back changes only the bytes it means to; and a missing value stays missing. Two of the toolkit's three 2026-10-03 IFC-Bench defects were IFC-to-BOS conversion errors (a doubled property set, material layers read at the wrong attribute position), the kind a second, mature reader would expose.

## Brainstorm

Goal: find where IfcOpenShell and the toolkit fit together so that a Python user or a Bonsai user gets something they cannot get today (an analysis as a replayable graph, tables across sources, byte-exact edits, a measured answer from Claude), and the toolkit gets a portable IFC reader, a reference to check its own conversion against, a write API with full schema coverage for script nodes, and a route to the largest open BIM community, without giving up its principles (one edit path, nothing writes until Run, honest absence, runs as evidence, tables as the currency). Also: decide honestly whether the toolkit should keep its own IFC layer at all.

Ideas, grouped by theme. Tags name the prompt that produced the idea.

### IfcOpenShell as a second IFC-to-BOS reader

1. `ifc2bos.py`: a Python converter, `ifcopenshell.open` to the three BOS tables (entities, parameters, relations) as Parquet, using `util.element.get_psets`, `get_container`, `get_type`, and `get_material`. Output loads with `bos.load` unchanged. (extends `bos.load` in `src/flow/BimOpenFlow.Nodes.Bos` and the `ifc_to_bos` tool in `BimOpenMcp.Ifc`)
2. A conversion oracle: convert every public sample with both readers and diff the BOS tables (row counts per property set, relation counts per kind, distinct values). The doubled 'Abmessungen' set and the misread `IfcMaterial.Category` from TKT-145 would each show as a count mismatch. (borrow from biology: redundancy; extends the comparison harness in `deps/bim-open-data/tests/data/Ara3D.IfcMeshingComparison`)
3. The portable path for workflow 1: on Linux and macOS, `bimopen-ifc` converts through `ifc2bos.py` instead of web-ifc's native DLL, so the one-command install no longer requires Windows. (what if the obvious dependency were forbidden)
4. IFC4X1 and IFC4X2 files, which the toolkit's loader does not list, fall back to the IfcOpenShell reader. (extreme: every schema)
5. Read `Ifc2Sql`'s SQLite output with the existing `sqlite.tables` and `sqlite.query` nodes: no new code, one table per IFC class, useful the day a user already has such a file. (what if it already existed; extends the Tables pack)
6. A view layer that presents an `Ifc2Sql` database as BOS (`CREATE VIEW` statements over its per-class tables), so a graph built on BOS runs on it. (borrow from databases: views as adapters)
7. In the browser for the public pages: npm `ifcopenshell` parses a dropped IFC, a small script fills BOS tables in DuckDB-WASM, and a sample graph runs with nothing installed. Compare with IFClite's parser for the same job (ifc-flow brainstorm, idea 2). (extreme: zero install)
8. A streamed reader for very large files: `ifcopenshell.stream` (present in the 0.9.0 package) feeding BOS rows without holding the model, measured on Snowdon's 456,598 instances. (extreme: the largest model)

### Geometry

9. IfcOpenShell's `geom.iterator` as a third mesher in the meshing comparison (`deps/bim-open-data/bench/ifc-mesher`, which already uses IfcOpenShell's sample house `IfcOpenHouse_IFC4.ifc`): per element, vertex count, volume, and bounding box against `Ara3D.Ifc.Mesher` and web-ifc. (borrow from testing: a reference oracle)
10. IfcConvert to GLB on Linux, then the toolkit's GLB reader fills BOS geometry: no native web-ifc build on that platform. (recombine)
11. The `manifold` kernel as a target: compare its output and speed with the toolkit's C# mesher on the slowest files in the ifc-mesher scorecard. (competition as a test)
12. `ifc_render` as the picture fallback: when the 3D pane is not running, a graph's colouring table goes to IfcOpenShell's renderer for a PNG in the notebook. (what if the viewer were absent; workflow 3)
13. SVG floor plans from IfcConvert or `ifcopenshell.draw`, coloured by a toolkit result table keyed by GlobalId, as a report figure. (borrow from architecture: the plan is the deliverable)

### The write path

14. `sink.ifcApi`: an Effect node that takes a table of rows (`function`, `params` as JSON) and applies them with `ifcopenshell.api` inside a Run, writing a new file, never the source. Every edit Claude proposes becomes a row a person can read before the Run. (extends `sink.writePsets` in `BimOpenFlow.Nodes.Effects`; principle 2)
15. Hybrid byte-exact writes: `ifcopenshell.api` builds the new entities (a classification reference, a material set, an element quantity), then `Ara3D.Ifc.Editing`'s `IfcPatcher` splices only those lines into the original file. Their schema knowledge, the toolkit's byte discipline. (recombine)
16. Base quantities where the model has none: `ifc5d`'s `IFC4QtoBaseQuantities` computes them into a copy, the toolkit reads them as BOS parameters marked as computed, and the source file is never changed. A computed area labelled computed keeps principle 3; an unlabelled one breaks it. (what if the missing value could be derived honestly)
17. A write-back parity test: the same property edits through `sink.writePsets` and through `ifcopenshell.api.pset.edit_pset` plus `file.write`, then a byte diff of both against the original. Settles whether the toolkit's claim holds. (borrow from biology: two writers, one diff)
18. Contribute byte-exact splicing upstream, as an `ifcpatch` recipe or a write mode that copies untouched byte ranges verbatim. (economics: give away the one thing the toolkit does best, to the project most people use)
19. `ifcpatch` recipes as one node kind, `ifc.patch`, with the 38 recipe names as an enum and each recipe's docstring in the generated catalog; Effect, output to a new file. (extends catalog generation in `BimOpenFlow.NodeDocs`)

### Script nodes (workflow 4, TKT-162)

20. Python script nodes with `ifcopenshell` importable: input tables arrive as Parquet, the IFC path as a parameter, a table returns with a declared schema (TKT-207). TKT-162's option 3, chosen because the largest body of IFC scripts in the world is Python. (what if the language were chosen by who already writes the scripts)
21. Purity by inspection: a script that imports `ifcopenshell.api` or calls `write` is classed Effect and waits for a Run; a script that only opens and reads may be Pure. A static scan of imports and calls decides; when unsure, Effect. (borrow from compilers: effect analysis)
22. `ifc.select`: the selector language as a parameter kind, so "IfcWall, IfcSlab" plus a property filter returns an entity table. Users of IfcOpenShell already know the syntax. (borrow)
23. Snippets from OSArch, the Academy, and the Impertio skill package wrapped as catalog entries, each with a test on a public sample, so community code becomes nodes with documentation. (economics: harvest existing work)
24. Pyodide script nodes in the notebook's public pages: the same Python script runs with no host, using the wasm-wheels build. (recombine 7 and 20)
25. A conversion from an `ifcopenshell.api` call to a node: Claude finds a function with `ifc_docs`, and a generated node kind wraps it with typed parameters taken from the function's signature. 384 candidate nodes, generated, never hand-written. (extreme: the whole API as nodes)

### Checks, standards, and comparison tools

26. `ifctester` stays TKT-50's parity reference (already decided in `ids-reuse.md`); its `Sqlite` reporter output is read by `sqlite.table`, so the parity diff is itself a graph with a run record. (extends `run-ifctester.py` in bim-open-data)
27. `ifctester`'s `Bcf` reporter beside the toolkit's uncommitted BCF writer (TKT-171): same failures, two BCF files, compare topic by topic. (redundancy)
28. IDS authored in ifctester.org's web editor goes straight into `check.ids` once it exists; the toolkit does not build an IDS editor. (what if someone else built the hard part)
29. `ifcclash` to refine the toolkit's bounding-box candidates into confirmed clashes. The brief puts clash detection beyond bounding boxes out of scope, so this stays a note unless the owner reopens it. (scope test)
30. `ifcopenshell.validate` as a gate in `bimopen-ifc`: on open, schema and EXPRESS rule failures are attached to every answer about that file. Same idea as the buildingSMART brainstorm's idea 15, with the checker already in hand. (what if the model were broken)
31. `ifcdiff` output (JSON) as a table: two revisions in, changed elements out, coloured in 3D. (invert: a diff tool becomes a data source)

### Claude, MCP, and the benchmark

32. A benchmark arm with `ifcopenshell-mcp`: the IFC-Bench subset from TKT-145, the same Claude model and effort, scored for correctness, time, and tokens beside the toolkit arm and a bare arm. ## Tensions

- **Compete or contribute, again.** `ifcopenshell-mcp` arrived in April 2026 and already covers what `bimopen-ifc` does for simple questions, plus editing, validation, clash, and pictures, from the team with the deepest IFC knowledge in open source. The toolkit's IFC server is defensible only where tables, SQL across sources, honest absence, and replayable runs give better answers, and that has to be shown by the benchmark (idea 32), not asserted.
- **Object model against tables.** IfcOpenShell's strength is a faithful object graph that a script walks and mutates; the toolkit's is immutable tables that DuckDB queries. Converting between them loses something each way: BOS drops IFC attributes that are not parameters (TKT-145's material positions were one case), and an object graph makes "per storey, per type, totals" a loop instead of a query.
- **Re-serialisation against byte-exact.** If `file.write` re-serialises, any IfcOpenShell write path breaks the toolkit's "every other byte identical" claim unless writes are spliced (idea 15). If it does not, the claim is less distinctive than `docs/CONTRIBUTIONS.md` says. Idea 17 decides which.
- **A Python dependency in a .NET host.** A subprocess keeps the host MIT and simple but adds a Python install, version pinning, and a process boundary to every IFC call; P/Invoke into the C++ library avoids Python but adds a native build per platform, which is the problem web-ifc already causes.
- **Licences.** LGPL-3.0 lets an MIT program call IfcOpenShell as a separate process, or link it dynamically, without changing the program's licence; shipping IfcOpenShell binaries with the toolkit obliges offering their source and letting users replace them; modifying IfcOpenShell keeps those modifications LGPL. **inferred** (general reading of LGPL-3.0, not legal advice) Code that imports Bonsai or IfcSverchok is GPL-3.0, so a Bonsai panel (idea 39) must be published under GPL in its own repository. Builds that include the CGAL kernel may carry GPL terms. **inferred**
- **One edit path.** Principle 1 says every edit goes through the same graph operations. An `ifcopenshell.api` call in a script node edits the IFC model, not the graph; that is allowed only if the call happens inside a node's Run (ideas 14, 21), never from Claude directly against the user's file.
- **Which workflow it serves.** Ideas 3, 7, 38 serve workflow 1; 1, 2, 33, 34 serve workflow 2; 12, 13, 39 to 42 serve workflow 3; 14, 20 to 25 serve workflow 4; 2, 9, 11, 17, 32, 46 serve workflow 5. Principle 9 says the first piece of work names one.

## Approaches

1. **Benchmark first** (ideas 32, 33, 46, 17): add an `ifcopenshell-mcp` arm to the IFC-Bench run and run the write-back parity test. Good because the IFC-Bench runner exists, the arm is one MCP configuration plus the `ifc-ask` guide's equivalent for the other server, the cost is about $7 a run, and the answer tells the owner whether `bimopen-ifc` earns its upkeep; fails to give users anything new, and the numbers may favour IfcOpenShell on geometry and edit questions.
2. **Second reader and oracle** (1, 2, 4, 5, 9, 10): a Python IFC-to-BOS converter used first to check the toolkit's own conversion and meshing, then as the reader on Linux and macOS. Good because conversion defects are where the toolkit has lost IFC-Bench points, and because it opens the portable path in workflow 1; fails if two converters drift and every difference becomes a ticket, or if the Python dependency makes the one-command install harder rather than easier.
3. **Python script nodes over IfcOpenShell** (14, 20 to 25): answer TKT-162 with Python and make the IfcOpenShell API the standard library of script nodes, with Effect classification and Run-gated writes. Good for workflow 4 and for IfcOpenShell's users, whose existing scripts become nodes; fails if a Python runtime in the host costs more than it returns, or if purity cannot be decided reliably.
4. **Hybrid write path** (15, 16, 17, 18, 19): IfcOpenShell computes, the toolkit splices; base quantities and classifications become writable without breaking byte identity. Good because it extends write-back from property sets to anything the API can build; fails if spliced entities reference ids that collide with the original's, or if parity (idea 17) shows IfcOpenShell already preserves bytes.
5. **Converge** (43, 47, 48, 53): send BOS and byte-exact splicing upstream, replace web-ifc with IfcOpenShell, or make the toolkit a layer over it. Good for reach and for maintenance cost, since the IFC layer stops being the toolkit's problem; fails if the maintainers do not want the contributions, and it binds the toolkit's IFC behaviour to a project the owner does not control.

## Recommendation (soft; the user asked for evaluation afterwards)

Approach 1 first, then approach 2's oracle (idea 2). `ifcopenshell-mcp` is the most direct alternative to `bimopen-ifc` a Claude Code user can install today, so the benchmark arm (idea 32) answers the question workflow 5 exists to answer, at the cost of one MCP configuration and about $7. The write-back parity test (idea 17) is an afternoon and settles whether byte-exact editing is still a distinguishing claim. Next, the oracle: a short `ifc2bos.py` diffed against the C# converter on the public samples would have caught two of TKT-145's three defects, and the same script is the seed of the portable reader (ideas 1, 3) if the owner wants Linux. Leave approach 3 to the TKT-162 decision, but record IfcOpenShell's API as the strongest argument for Python there. Keep the uncomfortable options (47, 48) open until the benchmark result exists; if the IfcOpenShell arm scores as well as the toolkit's on IFC-Bench, idea 48 deserves a real decision.

## Decisions for the user

- Which workflow does the first IfcOpenShell work serve? Default: workflow 5 (the `ifcopenshell-mcp` arm and write-back parity).
- Is `ifcopenshell-mcp` added as an arm of the IFC-Bench run (idea 32)? Default: yes, on the same 100-question subset with Claude Haiku 4.5 at medium effort, so the score compares with the toolkit's 62.
- Is a Python IFC-to-BOS converter written as a test oracle (idea 2)? Default: yes, in bim-open-data's tests, not shipped, until the oracle's results justify shipping it.
- Does TKT-162 (script node language) take IfcOpenShell into account? Default: yes; add a note to the ticket naming IfcOpenShell's API and community as the case for option 3, without deciding it here.
- Is IfcOpenShell allowed as a shipped dependency (ideas 3, 47)? Default: no, until the oracle and the benchmark exist; then decide between a subprocess and the npm WASM build, not P/Invoke.
- Is contact with the IfcOpenShell maintainers wanted (ideas 18, 36, 43, 46, 53)? Default: not before the parity test and benchmark results exist; then idea 18 (byte-exact splicing upstream) first, because it gives before it asks.
- Does `docs/CONTRIBUTIONS.md` get its own IfcOpenShell row? Default: yes, separate from xBIM and web-ifc, saying IfcOpenShell is the reference parser, IDS checker, and MCP server the toolkit measures against.
