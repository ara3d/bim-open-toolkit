# ifc-flow and IFClite: comparison and integration brainstorm

> Brainstorm, 2026-10-11. An honest comparison of BIM Open Toolkit with two open-source projects by Louis Trummer (GitHub `louistrue`, LT+ AG): ifc-flow (https://github.com/louistrue/ifc-flow), a browser node editor over IFC, and IFClite (https://github.com/LTplus-AG/ifc-lite), an IFC engine with its own flow graphs, followed by a wide, unjudged list of integration ideas, the tensions, five grouped approaches, and a soft recommendation. These are the closest things to direct competitors of the toolkit's node-graph product (BimOpenFlow), so the comparison comes first and says where each side is stronger. Nothing here is decided; the next step is to pick ideas and evaluate them (the `platonic:investigate` skill for a spike, `platonic:no-new-wheels` for reuse). Facts about the two projects were checked on 2026-10-11 against a shallow clone of ifc-flow at commit `46d56f5` (2025-12-15), IFClite's `main` at `a44434a` (2026-10-11) through raw files and the GitHub tree API, the GitHub REST API, api.npmjs.org, pypistats.org, and IFClite's `docs/` folder; they are marked **docs**. Facts about the toolkit come from this repository and are marked **docs** too. Everything else is **inferred**. Neither project is mentioned anywhere in this repository before this document; `docs/CONTRIBUTIONS.md` has no row for either.

## What they are, in the terms this repository uses

- **The author and the relation between the two.** Both are led by `louistrue`, who made 113 of ifc-flow's 114 commits and 3,664 commits to IFClite (the next contributor, `BIMvoice`, has 1,217). **docs** ifc-flow does not use IFClite: its source has no reference to it, and its IFC work goes through IfcOpenShell and web-ifc. **docs** IFClite's Flow (`@ifc-lite/flow`, `@ifc-lite/flow-nodes`) covers everything ifc-flow's palette does and adds a CLI, an MCP host, capability grants, and tests, so in practice it is ifc-flow's successor; ifc-flow's `master` has had no commit since 2025-12-15. **inferred**
- **ifc-flow.** A Next.js 14 web app with a React Flow 11 canvas, deployed on Vercel at ifcflow.com, licensed AGPL-3.0 (GNU Affero General Public License: anyone who runs a modified copy as a network service must publish its source). IFC is parsed in a web worker by IfcOpenShell 0.8.4, a Python library compiled to WebAssembly and run through Pyodide 0.28 (the README still says 0.8.1), with web-ifc 0.0.68 and three.js 0.174 for the viewer node. **docs** The model travels between nodes as a JavaScript object (`IfcModel` with an `elements` array), and node settings are `properties?: Record<string, any>`. **docs** (`components/nodes/node-types.ts`)
- **ifc-flow's nodes.** 19 node types, each a React component in `components/nodes/` plus one `case` in the 2,109-line `lib/workflow-executor.ts`: IFC, geometry, filter, transform, quantity, property (get, set, add, remove), material, classification, spatial, relationship, analysis (clash and space analysis), cluster, data transform, Python, export (CSV, Excel, JSON, IFC, GLB), viewer, watch, parameter, and AI. **docs** A Python node runs user code against IfcOpenShell in the browser; it is the only way to add behaviour without editing the app. **docs** Workflows are saved in the browser's `localStorage`. **docs** (`lib/workflow-storage.ts`)
- **ifc-flow's AI.** The AI node is a chat panel (`useChat` from the Vercel AI SDK) that posts to a Next.js route, `/api/chat`, which calls a model through OpenRouter with two tools, `discoverSchema` and a SQL query over an IfcOpenShell SQLite export of the model (IfcOpenShell's `ifc2sql`). The route adds Cloudflare Turnstile and rate limiting. **docs** The assistant answers questions; no tool edits the graph. **inferred** from the route's tool list. There is no MCP server. **docs**
- **IFClite, the engine.** A Rust core compiled to WebAssembly for parsing and geometry, a WebGPU renderer, and, by the README's count, 51 npm packages, 7 Rust crates, and a Python wheel (`ifclite-geom` 4.15.0); the GitHub tree holds 61 `package.json` files under `packages/` and 11 `Cargo.toml` files under `rust/`, and the repository description still says "30+ TypeScript packages and 5 Rust crates". **docs** Licence MPL-2.0 (Mozilla Public License, file-level copyleft: modified files stay MPL, the rest of a program can be anything). **docs** It reads IFC2X3, IFC4, IFC4X3 (the README claims all 776 IFC4 and 876 IFC4X3 entities), and IFC5 in its JSON form, IFCX. **docs** Geometry runs on an exact-arithmetic CSG (constructive solid geometry) kernel that the README says agrees with IfcOpenShell element by element on "99.9%+" of its public benchmark corpus. **docs**
- **IFClite's data model.** A columnar in-memory store: typed arrays of express ids, type enums, and name indices over an interned string table, a relationship graph in CSR (compressed sparse row) form, and properties extracted lazily on first access. **docs** (`docs/architecture/data-flow.md`, `docs/guide/performance.md`) SQL is available through DuckDB-WASM, downloaded on the first `query.sql()` call, and `ParquetExporter` writes the tables as Parquet. **docs** This is the same shape as BIM Open Schema (BOS, the toolkit's table format: entities, parameters, and relations as flat tables over pooled strings), arrived at independently. **inferred**
- **IFClite's IFC writing.** `MutablePropertyView` records property edits with undo; `StepExporter` writes one line per source record it keeps, rewrites the lines whose attributes changed, and appends generated property sets; it can also convert schema (for example IFC4 to IFC2X3) and create files from scratch (`@ifc-lite/create`). **docs** (`packages/export/src/step-exporter.ts`, `step-source-iteration.ts`) The documents do not claim that untouched bytes come out identical. **inferred**
- **IFClite's Flow.** A `*.flow.json` document (`flowVersion`, `capabilities`, `inputs`, `outputs`, `nodes`, `edges`) that runs in the viewer's Flow panel (`@xyflow/react` 12), headless with `ifc-lite flow run` in CI, and through the MCP tool `run_flow`. **docs** Values on an edge are an item, a list, or a group (lists keyed by string); entities are handles (`{ globalId, modelId?, expressId? }`), not copies; table columns carry their IFC value type, an optional unit, and the property set and property they came from. **docs** (`docs/guide/flow.md`) A node is a TypeScript object, `FlowNodeDef`, with `type`, `title`, `category`, `doc`, `inputs`, `outputs`, `params`, `capabilities`, `reads`, and `run`. **docs** (`packages/flow-nodes/src/model-nodes.ts`) I counted 81 node types in `@ifc-lite/flow-nodes` 0.7.0: `core.*` (17), `model.*` (16), `table.*` (11), `element.*` (6), `viewer.*` (5), `ai.*` (4), `bcf.*` (3), `ids.*` (3), `report.*` (3), `script.*` (2), `session.*` (2), `documents.*` (2), `aps.*` (2), and one each of `http.request`, `speckle.receive`, `geometry.point`, `validation.runChecks`, `comparison.runChecks`. **docs** (counted from `type:` declarations; may miss nodes declared another way)
- **IFClite's evaluation and effects.** A `MemoCache` recomputes only nodes whose inputs, parameters, or model revision changed; each write bumps a write generation; network nodes are never memoised. **docs** A graph declares capabilities (`model.read`, `model.mutate:Pset_WallCommon`, `model.create`, `network.fetch:<host>`, `secret.read:NAME`, `network.ai`), and every node checks the exact grant before acting, so a grant for one property set does not let a node write another. **docs** Writes land in a change set and a whole run is one undo step. "Tracked" creation nodes derive each element's GlobalId from a tracking key, so a re-run creates, updates, keeps, or removes elements instead of duplicating them, with the tracked sets in a sidecar file. **docs** AI nodes pause the run for review; a checkpoint holds a digest of the graph and inputs, a digest of the sources read, and a digest of the proposal, and a resume restores completed nodes without re-running them. **docs** Script nodes run JavaScript in a QuickJS sandbox whose permissions follow the graph's grants. **docs**
- **The mapping corpus (pull request 5925).** Merged on 2026-09-25, it added `speckle.receive`: a Speckle model version in, IFC walls, slabs, roofs, columns, and beams written into a target storey through `bim.store.add*`, Revit parameters as `Speckle_TypeParameters` and `Speckle_InstanceParameters` property sets. **docs** Its contract is a mapping table in `docs/architecture/speckle-mapping.md`; anything it cannot map leaves on a `refusals` output with a reason (`unmapped-type`, `missing-dimension`, `no-units`, `display-meshes`, and six more), and a dimension is read only if its unit converted as a length. It is tested against a hand-authored fixture corpus in `packages/flow-nodes/src/__fixtures__/speckle/`, run by unit tests and by a CLI test, so no live server is needed. **docs** The node declares `writes: 'model'` and needs `model.create`, `model.delete`, three exact `model.mutate:Speckle_*` grants, and `network.fetch` for the Speckle host. **docs**
- **IFClite's AI.** `@ifc-lite/mcp` (also `ifc-lite mcp model.ifc`) exposes about 120 tools in 19 groups (a few marked planned), among them query, geometry, clash, IDS validation and authoring, mutation, hosted modelling, BCF, bSDD, diff, export, Flow (`describe_flow`, `run_flow`, `propose_flow`, `resume_flow`), a live viewer driven by the agent, and draft layers with review. Tools carry a scope (`read`, `validate`, `export`, `mutate`, `admin`), and the server hides tools outside the session's scope at listing time. It ships prompts such as `audit_model` and `clash_review`. **docs** (`docs/guide/mcp.md`) The viewer has an Assistant with the user's own Anthropic or OpenAI key that discusses frozen snapshots of panel results, and `ifc-lite ask model.ifc "..."` answers from the terminal. **docs**
- **IFClite's tests and benchmarks.** A fixture corpus of 182 IFC files pinned by SHA-256 in `tests/models/manifest.json`, 28 of them under `ara3d/` with the names of the files in Ara 3D's IFC test set (`duplex.ifc`, `schependomlaan.ifc`, `FM_ARC_DigitalHub.ifc`, `AC20-FZK-Haus.ifc`). **docs**; that they come from Ara 3D's repository is **inferred**. CI holds performance "ratchets" (ceilings on instruction counts and bundle bytes that fail a pull request when exceeded and lower themselves daily). **docs** About 4,600 files in the tree are tests by name. **inferred** (counted by file name pattern)

Read plainly: IFClite is a much larger, faster-moving, more widely used project than the toolkit, and its Flow is ahead on the effect model and on engine speed. ifc-flow is an earlier prototype that IFClite's Flow has overtaken. The toolkit's distinct claims are narrower and specific: a graph whose result is a replayable, content-hashed record; tables and SQL as the medium for every kind of output; write-back that changes only the bytes it means to; and a Claude-in-Claude-Code workflow aimed at people who do not write code. Two of IFClite's choices overlap the toolkit's principles closely enough to be worth naming: refusals and `problems` outputs instead of coerced values are honest absence (principle 3), and capability grants with review checkpoints are a finer-grained form of "nothing writes until Run" (principle 2).

## Brainstorm

Goal: find where IFClite (and, through it, ifc-flow's users) and the toolkit fit together so that an IFClite or ifc-flow user gets something they cannot get today, and the toolkit gets a fast IFC parser in the browser, a node vocabulary to measure itself against, a mapping discipline for the Speckle converter, and access to a far larger audience, without giving up its principles (one edit path, nothing writes until Run, honest absence, runs as evidence, tables as the currency). Also: decide honestly whether two node editors from these two camps should both exist.

Ideas, grouped by theme. Tags name the prompt that produced the idea.

### IFClite's parser inside the toolkit

1. An `ifclite.load` node: IFC bytes in, the three BOS tables (entities, parameters, relations) out, built from IFClite's columnar store in Node. Pure, keyed by the file's content hash like `bos.load`. (extends `bos.load` in `src/flow/BimOpenFlow.Nodes.Bos` and the content-hash cache rule in `docs/nodes.md`)
2. IFC in the browser for the public pages: the notebook page loads `@ifc-lite/wasm`, parses a dropped IFC file, writes BOS-shaped tables into DuckDB-WASM, and a graph runs over them with no host. Today the public pages carry BOS geometry and recorded snapshots, not a parser. (extreme: zero install, workflow 1)
3. A third parser in `Ara3D.IfcMeshingComparison`: IFClite's exact-CSG meshes beside web-ifc's and `Ara3D.Ifc.Mesher`'s, one discrepancy table per element. (borrow from testing: an oracle; extends `deps/bim-open-data/tests/data/Ara3D.IfcMeshingComparison`)
4. Drop the native `web-ifc-library.dll` for geometry and call IFClite's native Rust geometry through its FFI crate (`rust/ffi`) or its Python wheel, ending a C++ dependency that pins the toolkit to `net8.0-windows`. (what if the obvious dependency were forbidden)
5. IFCX support for free: IFClite reads IFC5 JSON, so `ifclite.load` gives the toolkit the IFCX source that `docs/CONTRIBUTIONS.md` says "could be a BOS source". (what if it already existed)
6. Use IFClite's parser as the speed baseline in the Snowdon first-frame budget: their Snowdon Towers structural file (8.3 MB, 147,142 entities) loads in 3.7 s in their CI; the toolkit takes 5.2 to 5.8 s to a first frame of its private Snowdon model (456,598 instances). Measure both on the same file and machine. (competition as a test)

### The toolkit's tables inside their Flow

7. A `bos.load` node for IFClite Flow: a `.bos` file or a BOS Parquet folder in, a `Table` of entities with typed, unit-carrying columns out, so a Revit export made by the toolkit's add-in reaches an IFClite graph with no IFC. (invert: source becomes their source)
8. BOS as an IFClite "source" package beside `source-autodesk`, `source-dalux`, `source-dropbox`: `@ifc-lite/source-bos`, reading the same Parquet the toolkit writes. (extends their `packages/source-*` pattern)
9. A `duck.query` node for IFClite Flow: SQL over a table, through the DuckDB-WASM they already lazy-load, returning a table with declared column types. Their tables gain the toolkit's main operation. (borrow from the toolkit's vocabulary: `duck.query`, `sql.query`)
10. Their `ParquetExporter` output read straight by the toolkit's `parquet.read`, and the toolkit's BOS Parquet read straight by their query layer: agree on column names and nothing else. (what if a file format were the integration)
11. A BOS-to-IFClite-store adapter in the reverse direction: their viewer opens a BOS model by building the columnar store from BOS tables, so the toolkit's Revit and Speckle-made models get their renderer, clash, and IDS. (what if we supplied what they lack: non-IFC sources)

### One catalog, one graph format

12. A shared node catalog format: a JSON schema covering both `NodeSpec` (ports, parameter kinds, purity, suggestion sources) and `FlowNodeDef` (access, capabilities, reads, writes). Each side generates it; `docs/nodes.catalog.json` is the toolkit's half. (extends `BimOpenFlow.NodeDocs` and `docs/nodes.catalog.json`)
13. Their vocabulary as a checklist against `docs/nodes.md`: every IFClite node kind mapped to a toolkit kind or marked missing. A first pass finds the toolkit has no `element.*` creation, no `bcf.*`, no `ids.*` node, no `http.request`, no `table.joinByKey` with an `ambiguous` output, and no list-and-group restructuring nodes such as `core.groupBy`; IFClite has no `table.window`, `date.*`, `spatial.polygon*`, `rel.*`, or `sink.exportSqlite`. (borrow from auditing: a gap table)
14. A `.flow.json` importer in the toolkit: read their graph document, map each node kind through the table from idea 13, and open it in the studio with unmapped nodes shown as `Unavailable`. (what if a person brought their graph)
15. The reverse exporter: a toolkit graph saved as `.flow.json` where every node has a counterpart, so an IFClite user runs it with `ifc-lite flow run`. (invert)
16. Their `capabilities` header added to the toolkit's graph document as a fourth layer beside `structure`, `values`, `layout`, `session`: a graph says which property sets its Run may write, and `sink.writePsets` checks the exact name. (extends `sink.writePsets` and the graph document in `docs/ARCHITECTURE.md`)
17. Conformance vectors for their engine: the toolkit's `deps/ara3d-dataflow/spec/` vectors translated into `.flow.json` where the semantics match, so "two engines, one specification" becomes a test either side can run. (borrow from standards bodies: a test suite as the standard)
18. A joint catalog maintained by both projects, with a buildingSMART-style working group, so the next BIM node editor starts from it. Listed because a joint catalog may be the best outcome of all. (outside software: standards)

### Graphs that run across both

19. An `ifclite.flow` node in the toolkit: runs a named `.flow.json` through `ifc-lite flow run --json` as a subprocess and returns its graph outputs as tables, so an IFClite clash or IDS graph is one node in a toolkit graph. Pure for read-only graphs; Effect when the graph declares a write capability. (recombine)
20. The reverse: an IFClite `toolkit.run` node that calls the toolkit host's HTTP API to evaluate a named analysis and returns its result table, with the run id as provenance. (recombine, invert)
21. A shared run record: their checkpoint already holds a graph digest and a source digest; extend it to the toolkit's run-record shape (graph hash, input content hashes, outputs) so a cross-engine graph has one record. (extends `DataFlowEngine.Runs`)
22. Their tracked writes for the toolkit: `sink.writePsets` keyed by a tracking key and GlobalId, so re-running an enrichment graph updates the same property sets rather than appending, with the tracking sidecar beside the run record. (borrow from their `model.addElement` tracking)
23. Their review checkpoint as the toolkit's Run approval: a Run that writes pauses at the effect node, shows the diff, and resumes on approval of a digest. "Nothing writes until Run" becomes "nothing writes until a person approves this exact diff". (what if the limit were the feature)

### Benchmarks

24. A fourth arm in the workflow 5 benchmark: the same questions answered by Claude over `@ifc-lite/mcp`, scored on correctness, time, and tokens beside the toolkit arm and the bare arm. (what if a competitor did it their way)
25. IFC-Bench (TKT-145) run through `ifc-lite ask` and through their MCP server with the same Claude model, published side by side with the toolkit's 62 of 100. The comparison either side would cite. (competition as a test)
26. A shared fixture manifest: their `tests/models/manifest.json` already pins 28 files from Ara 3D's set by SHA-256; adopt the same manifest format for the toolkit's public samples so both suites name models identically. (what if it already existed)
27. Parse and first-frame numbers for the toolkit published in the same table shape as theirs (file size, entities, meshes, total load, date, machine), committed and regenerated, like their `perf-numbers` block. (borrow from their CI: generated, dated numbers)
28. A perf ratchet in the toolkit for the Snowdon first frame: a ceiling that fails a push when the first frame gets slower and lowers itself when it gets faster. (borrow from their ratchets; see the tooling ledger in `docs/plans/visualization/TOOLING-LEDGER.md` before adding one)

### A shared IFC write path

29. A write-back parity test: the same property edits applied by `Ara3D.Ifc.Editing` and by IFClite's `StepExporter`, then a byte diff of the two outputs against the original. If theirs is byte-identical outside the edits, the toolkit's distinguishing claim narrows; if not, the toolkit has a contribution to offer. (biology: redundancy, two writers and one diff)
30. Contribute byte-exact splicing upstream: an IFClite export mode that copies untouched byte ranges verbatim and splices only changed entities, ported from `IfcSourceFile` and `IfcPatcher`. (economics: give away the one thing we are best at, to the project most people use)
31. Their `model.applyTable` semantics for the toolkit's `sink.writePsets`: an empty cell never deletes, an unparsable cell is reported per row and not written, ambiguous key matches go to their own output. (borrow: they wrote the honest-absence rules for writes down already)
32. IFClite's mutation overlay as the edit model for the toolkit's 3D pane: a person sets a property on a selected element, it lands as a pending change, and a Run writes it byte-exactly. (recombine 29 and 31)

### The viewer

33. ## Tensions

- **Compete or contribute.** IFClite has about 100 times the stars, tens of thousands of monthly downloads, a team, and a Flow that already does tables, IDS, BCF, AI review, CI runs, and MCP. Building a second BIM node editor beside it costs the owner's time on a product with almost no users. Contributing (ideas 30, 42 to 46, 49) reaches people now but moves the toolkit's identity into someone else's project.
- **Entity handles against tables.** IFClite passes entity handles and reads through the SDK when a node runs; the toolkit passes immutable tables and lets DuckDB do the work. Handles keep memory low in a browser and make writes natural; tables make SQL, joins across sources, and replay natural. A shared catalog (ideas 12 to 18) has to state which one a port carries, and some nodes will not translate.
- **Effect model depth.** Their capability grants, tracked writes, and review checkpoints are finer than the toolkit's Pure and Effect split; the toolkit's run record is a fuller replay than their checkpoint. Taking one side's model wholesale loses what the other does well.
- **Licences.** MIT (toolkit) can use MPL-2.0 packages unmodified without changing licence; modifying IFClite's files keeps those files MPL. ifc-flow's AGPL-3.0 means code copied from it into a hosted toolkit page would oblige publishing the page's source, so take ideas from it, not code.
- **Which workflow it serves.** Ideas 2, 36 serve workflow 1 (look, then install one thing); 1, 19, 37 serve workflow 2; 33, 34 serve workflow 3; 41, 48 serve workflow 4; 6, 24, 25, 27, 29 serve workflow 5. Principle 9 says the first piece of work names one.

## Approaches

1. **IFClite as the toolkit's browser parser** (ideas 1, 2, 5, 52, 54): parse IFC with `@ifc-lite/wasm` into BOS-shaped tables, in Node for the host and in the browser for the public pages. Good for workflow 1, because a dropped IFC file answers questions with nothing installed, and for IFCX at no cost; fails if their columnar store cannot produce BOS parameters and relations without loss, or if a 2.6 MB gzipped WASM module is too heavy for a notebook page.
2. **Benchmark and parity first** (6, 24, 25, 26, 27, 29): put IFClite beside the toolkit on the same models, questions, and edits, and publish the numbers. Good because it answers "why not just use IFClite?" with evidence, which workflow 5 already demands, and costs little code; fails to give anyone a feature, and the numbers may favour them on most counts.
3. **Shared catalog and cross-running graphs** (12 to 21): one catalog schema, a gap table, import and export of `.flow.json`, nodes that call each other's runtimes. Good for users of both and for a joint catalog later; fails on the handle-against-table difference and costs both teams ongoing translation work.
4. **Borrow their discipline** (16, 22, 23, 31, 38, 39, 41, 42 to 45): adopt capability grants for writes, tracked writes, approval checkpoints, MCP scopes, the mapping corpus, refusals, and the unit rule, without depending on their code. Good because each idea is small, fits a principle the toolkit already holds, and two of them (42 to 45) apply to the Speckle converter being built now; fails to reach their users.
5. **Contribute and converge** (30, 46, 49, 55): send byte-exact write-back and BOS sources upstream, and consider building the toolkit's nodes as an IFClite pack. Good for reach and for the industry; fails if LT+ AG does not want them, and it hands the toolkit's main surface to a project the owner does not control.

## Recommendation (soft; the user asked for evaluation afterwards)

Approach 2 first, with approach 4 beside it. The comparison above shows IFClite stronger on most counts that a user notices, so the toolkit's first job is to find out, with numbers, where its own claims hold: run the IFC-Bench subset through `@ifc-lite/mcp` with the same Claude model (idea 25), and run the write-back parity test (idea 29). Those two facts decide everything else. If the toolkit's arm answers more questions correctly and its write-back is byte-exact where theirs is not, the toolkit's identity is "the evidence and write-back layer", and approach 1 (their parser underneath) and idea 30 (byte-exact splicing contributed upstream) follow. If their arm wins and their writer is already byte-exact, the uncomfortable options (49, 51) deserve a real decision rather than a list entry. Approach 4 costs little and helps now: the mapping corpus, the refusals table, and the unit rule (ideas 42 to 44) should go into TKT-185's chunks before the converter's reader is written. The tension that decides the order is compete or contribute, and it should be settled by the benchmark rather than by preference.

## Decisions for the user

- Which workflow does the first IFClite work serve? Default: workflow 5 (the benchmark arm and write-back parity), because it decides whether the toolkit competes or contributes.
- Is IFClite added as a fourth benchmark arm (idea 24) and to the IFC-Bench run (idea 25)? Default: yes, on the 100-question subset, at the subset's cost (about $7 a run).
- Do the Speckle converter chunks (TKT-185) adopt the mapping corpus, the refusals table, and the per-element unit rule (ideas 42 to 44)? Default: yes, before chunk D2 (the reader).
- Should the toolkit depend on `@ifc-lite/wasm` for IFC in the browser (approach 1)? Default: a spike only, measuring whether its store maps onto BOS without loss on the Duplex; no dependency until the spike passes.
- Is the toolkit's own node editor still in scope given IFClite's Flow (ideas 49 to 51)? Default: yes for now, revisited after the benchmark; record the question as a `kind: question` ticket beside TKT-4 (the user-facing noun).
- Is contact with LT+ AG about a joint catalog or upstream write-back (ideas 18, 30, 55) wanted? Default: not before the parity test result exists.
