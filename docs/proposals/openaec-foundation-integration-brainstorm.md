# OpenAEC Foundation integration: brainstorm

> Brainstorm, 2026-10-10. A wide, unjudged list of ways BIM Open Toolkit could work with the OpenAEC Foundation (https://github.com/OpenAEC-Foundation), followed by the tensions, five grouped approaches, and a soft recommendation. The foundation is a community and a publisher of tools and Claude skill packages, not one product, so most ideas are about distribution, conventions, and shared evidence rather than a data connector. Nothing here is decided; the next step is to pick ideas and evaluate them (the `platonic:investigate` skill for a spike, `platonic:no-new-wheels` for reuse). Facts were checked on 2026-10-10 against the GitHub API, the repositories' READMEs, open-aec.com, skills.sh, agentskills.io, and one OSArch forum thread, and are marked **docs**; everything else is **inferred**. The only earlier mentions in this repository are two lines in `docs/proposals/speckle-integration-brainstorm.md` (fact 12 and idea 32), which credit the Speckle skill package to the foundation; that credit is now out of date (see below).

## What the OpenAEC Foundation is, in the terms this repository uses

- **Who runs it.** A Dutch foundation in formation ("Stichting i.o."), based in Dordrecht. The board on open-aec.com is Maarten Vroegindeweij (chair and initiator), Jochem Kolthof (treasurer), Martjan den Hoed (secretary), and Silvia Taurer. The GitHub profile gave 2026-03-01 as the planned founding date; on 2026-10-10 the website still says "i.o.". **docs** The GitHub organisation was created on 2025-12-24 and has 63 public repositories and 210 followers; most repositories were created in 2026. **docs** It is young and small: an OSArch forum reply in June 2026 called the plan to build about 30 apps "with a core team of 4 within one year" optimistic. **docs**
- **What it says it is for.** "Developing, supporting and promoting open source software for the entire construction chain", with the stated goal of making construction software open source by the end of 2026. Four pillars: development, support, education (student internships), advocacy for open standards. **docs** Community channels are a WhatsApp group, a feedback site (open-feedback-studio.open-aec.com), an Early Adopter Program, and GitHub. No membership fees, events calendar, or governance documents beyond "concept statutes" were found. **docs**
- **What it builds.** Desktop and web "Studios", mostly Rust, Tauri 2, WebAssembly, and three.js, many with Dutch-language READMEs: Open PDF Studio (904 stars, by far the largest), Open Planner Studio, Open Calc Studio (cost estimation), Open Calculations Studio (structural calculations in CalcPAD syntax with IFCX and IFC4x3 export), Open Heatloss Studio (ISSO 51), Open Pointcloud Studio, Open Geotechniek Studio (CPT files), Open 3D Studio (IFC modelling on That Open Engine), Monty IFC Viewer (built on the Speckle viewer), IFCCAD (Rust CAD drawing models, DXF and DWG), an IFC validator that checks IDS (Information Delivery Specification) files such as NL-BIM Basis ILS and the RVB BIM norm and exports BCF (BIM Collaboration Format) issues, and a BCF 2.1 issue platform. **docs** The OSArch thread says all tools use LGPL-3.0 and that "MCP servers [are] planned per tool"; in practice the repositories carry MIT, MPL-2.0, LGPL-3.0, CC-BY-SA-4.0, or no licence. **docs** The website names IFCX as the ecosystem's "universal data format". **docs**
- **OpenAEC Installer.** A Tauri app that lists every OpenAEC tool from `src/data/catalog.ts` (entries of `kind: "desktop"` with a GitHub repository and installer asset, or `kind: "web"` with a URL), detects installed versions, and installs or launches them. **docs** It is the foundation's version of "install one thing".
- **The Claude skill packages are not the foundation's repositories any more.** skills.sh lists 8 sources under `openaec-foundation`: 177 skills, 304 installs in total (ThatOpen 18 skills and 90 installs; the Delft workshop 61 and 70; Speckle 25 and 50; n8n 21 and 42; Tauri 2, SolidJS, the Workspace Composer, and Draw.io the rest). **docs** The GitHub API redirects `OpenAEC-Foundation/Speckle-Claude-Skill-Package`, `ThatOpen-Claude-Skill-Package`, and `n8n-Claude-Skill-Package` to the `Impertio-Studio` organisation, which belongs to Impertio B.V. in Dordrecht and holds about 30 packages: IFC (50 skills), Blender-Bonsai-IfcOpenShell-Sverchok (73), Cross-Tech AEC (15), Three.js, QGIS, CesiumJS, PostgreSQL, Frappe (190 stars, the most starred), and others, all MIT. **docs** The Speckle package's only contributor is Freek Heijting, who is also the third-largest contributor to Open PDF Studio. **docs** So the packages are written by one person and company close to the foundation and were moved out of its organisation; the skills.sh listing still shows the old owner. **inferred**
- **How the packages are made.** `Skill-Package-Workflow-Template` describes a seven-phase method (bootstrap, research, masterplan, topic research, skill creation by three parallel agents, validation, publication) and a reusable GitHub Actions check: YAML frontmatter with a folded description and "Use when..." triggers, `SKILL.md` under 500 lines, a fixed folder layout (`core/`, `syntax/`, `impl/`, `errors/`, `agents/`), English only, and a compliance score of at least 90%. Skills are named `{tech}-{category}-{topic}`, for example `speckle-impl-viewer`, and written in "deterministic" ALWAYS and NEVER language. **docs**
- **What the packages contain.** Knowledge for writing code against a library: the Speckle package targets Speckle 2.x and 3.x (streams, commits, `operations.send`) and ships a Node MCP server with 13 tools; its last push was 2026-07-08, before Speckle's 2026.9 data model. **docs** It is therefore likely stale for the new data model. **inferred** The IFC package covers IFC2x3 to IFC5 and IFCx, EXPRESS, property sets, validation, and library choice, and installs with `npx skills add @openaec/ifc-claude-skill-package` or by copying `skills/source/`. **docs**
- **Workspace Composer.** A Tauri desktop app that writes a Claude Code workspace (`CLAUDE.md`, `.claude/settings.local.json`, `.claude/skills/`) from chosen packages and presets, for example `bim-web` (ThatOpen and Three.js) and `speckle-collab` (Speckle and Cross-Tech AEC). Its live registry, `src/lib/registry.ts`, lists repositories in the OpenAEC-Foundation organisation whose names match `*Skill-Package*` or `*Claude-Skill*`, plus `anthropics/skills`, and falls back to a hard-coded list. MCP servers, hooks, and commands are an alpha "advanced mode". **docs** Since the packages moved, the live query probably finds none of them and the app runs on its fallback list. **inferred**
- **The Delft workshop.** `Computational-Design-Day-Delft-March-2026` is a workshop repository: 61 skills for Blender, Bonsai, and IfcOpenShell, a Blender MCP entry in `.mcp.json`, a `CLAUDE.md`, and `session-1/` and `session-2/` folders for participants' tools. On 2026-10-10 `session-1/` holds only its README. **docs** No web listing for the event was found; the date and place come only from the repository. **docs**
- **The standard underneath.** The packages say they follow Agent Skills (agentskills.io), the open format Anthropic released: a folder with `SKILL.md`, required `name` (at most 64 characters, lowercase letters, digits, and hyphens, equal to the folder name) and `description` (at most 1,024 characters), optional `license`, `compatibility`, `metadata`, and `allowed-tools`, a body under 500 lines, and about 100 tokens of metadata per skill loaded at startup. `skills-ref validate` checks it. skills.sh is Vercel's directory and installs with `npx skills add <owner/repo>`. **docs** The toolkit's `bim-flow` (description 426 characters, 37 lines) and `ifc-ask` (351 characters, 17 lines) already fit the required fields. **inferred** from reading both files.

## Brainstorm

Goal: find a relationship in which the foundation's users (Dutch BIM practices, students, people who install skill packages into Claude Code) get answers about their models that they cannot get from knowledge skills alone, and the toolkit gets distribution, a shared skill format, an audience for its benchmark, and workshop material, without giving up its principles (one edit path, nothing writes until Run, runs as evidence, tables as the currency) or spending the owner's time on work no workflow names (principle 9).

Ideas, grouped by theme. Tags name the prompt that produced the idea.

### Publishing the toolkit's skills

1. Publish `bim-flow` and `ifc-ask` as a skills.sh source so `npx skills add ara3d/bim-open-toolkit` installs them. The folders already fit the standard; the work is a `license` field and a README section. (what if it already existed)
2. Rename the toolkit's skills to the foundation's pattern, `bimopen-impl-ifc-ask` and `bimopen-impl-flow`, so they sort beside `ifc-*` and `speckle-*` in a shared workspace. (borrow from a library catalogue: shelve by call number)
3. Add the foundation's reusable `skill-quality.yml` workflow to this repository's CI and keep its compliance score at 90% or more. A free external check on `.claude/skills/`. (extends the gates in `gates/`)
4. A `compatibility` field on each skill that says plainly what it needs: "Requires the bimopen-ifc MCP server (.NET 8, Windows)". Today a user who copies the folder alone gets a skill that names tools they do not have. (what if the obvious approach, copying a folder, were the only install)
5. Generate a third skill from `docs/nodes.catalog.json`: one `references/` file per pack (13 packs, 124 nodes), so a Claude session without the MCP server still knows what nodes exist and can write a graph document by hand. (extends `BimOpenFlow.NodeDocs`, which already generates `docs/nodes.md`)
6. Generate one skill per node pack instead, in the foundation's `{tech}-{category}-{topic}` naming: `bimopen-syntax-tableops`, `bimopen-syntax-spatial`. Thirteen small skills load only when a task touches that pack. (extreme: one skill per node)
7. A BOS (BIM Open Schema) knowledge skill: the tables, the closed relation vocabulary (`PartOf`, `ContainedIn`, `HostedBy`, `BoundedBy`), and DuckDB patterns, generated from `deps/bim-open-schema`. Useful to anyone holding a `.bos` file, with or without the toolkit. (what if the schema were the product)
8. Ask that the toolkit be listed in the Workspace Composer's registry as an "AEC/BIM" package, and add a preset "BIM Answers" (toolkit plus IFC plus ThatOpen). One pull request to `src/lib/presets.ts`. (what if the problem moved to someone else)
9. Fix the Composer's registry for them: it searches the OpenAEC-Foundation organisation, but the packages moved to Impertio-Studio. A pull request that adds a second source, or reads a manifest, is a useful first contribution and an introduction. (invert: give before asking)

### Bundling their skills with the toolkit's install

10. One Claude Code plugin that registers `bimopen-ifc` and `bimopenflow-duckdb`, the toolkit's two skills, and a pinned copy of the IFC package. Workflow 1's "one install" with IFC background knowledge included. (recombine)
11. Pin by commit, the way `deps.json` already pins the six sibling repositories, so a package update never changes an answer between benchmark runs. (extends `deps.json` and `deps.mjs`)
12. Bundle only the parts that do not overlap: the IFC package's `errors/` and `core/` skills explain IFC; the toolkit's tools compute answers. Skip their `impl/` parsing skills, which would steer Claude to write IfcOpenShell scripts instead of calling `ifc_sql`. (invert: subtract instead of add)
13. Bundle nothing; add a "Pairs well with" table to the README naming IFC, ThatOpen, Speckle, and Cross-Tech AEC, with the install line for each. (what if we did nothing)
14. Measure the cost of bundling before doing it: 177 skills at about 100 tokens of metadata each is roughly 17,700 tokens loaded at the start of every session, against a project that sells "how few tokens an answer costs". (extreme: every package installed)
15. A routing skill: one short `SKILL.md` that says "for a question about an existing model, use `ifc_sql`; for authoring IFC, use the IFC package". It keeps two sets of skills from competing for the same request. (borrow from networking: a routing table)
16. Bundle the Speckle package's MCP server beside the toolkit's, so a Speckle project can be listed and a version fetched in the same session. It targets Speckle 2.x, so check it against the 2026.9 data model first (see `speckle-integration-brainstorm.md`). (recombine with the Speckle brainstorm)

### Shared conventions

17. Adopt Agent Skills as the toolkit's skill contract and say so in `docs/ARCHITECTURE.md`, so the Ask box's system prompt (built from the same files) and the published skills cannot drift. (extends the rule that the three `bim-flow` guide files are also the Ask prompt)
18. Contribute back a convention the foundation lacks: "a number Claude reports comes from a tool result, never from memory" (principle 4) as an `agents/` rule in their template. Their "deterministic" language tells Claude how to write code; this tells it how to state a measurement. (borrow from laboratory practice: a measurement carries its instrument)
19. Contribute "honest absence" (principle 3) as a cross-tech error skill: a missing quantity stays NULL, never 0. It applies to every IFC-to-ERPNext costing pipeline their Cross-Tech package teaches. (what if a principle were a skill)
20. A shared test format for skills: a question, a model, and the expected answer as a table. The toolkit's benchmark questions become their skills' acceptance tests, and their CI checks behaviour as well as frontmatter. (borrow from compilers: conformance vectors)
21. Propose that skills which depend on an MCP server declare it in `metadata` (`mcp-server: bimopen-ifc`) and that the Composer installs the server when it installs the skill. Their advanced mode already has an MCP page. (extends an existing abstraction: the Composer's MCP Servers page)

### Their tools and the toolkit's nodes

22. IDS parity: run NL-BIM Basis ILS and RVB BIM norm, the two IDS files their validator ships, through the toolkit's IDS evaluator (`src/data/Ara3D.Ids`, TKT-50), and publish the per-check diff against their `ifctester` results. Two validators, one diff table. (biology: redundancy)
23. A `sink.bcf` effect node that writes their validator's BCF format from `check.rule` failures, so a toolkit check opens in their BCF platform. TKT-171 (BCF 3.0 export) already asks for this; their platform reads BCF 2.1. (extends `BimOpenFlow.Nodes.Effects`)
24. An IFCX reader or writer: the foundation names IFCX as its common format, and Open Calculations Studio exports it. A BOS-to-IFCX mapping would put toolkit results into their apps. (what if a file format were the integration)
25. The toolkit as an entry in the OpenAEC Installer's `catalog.ts`: `kind: "web"` pointing at the public sample pages, or `kind: "desktop"` once there is a release asset. Their users already open that app. (what if the install were somebody else's button)
26. Their Monty IFC Viewer and Open 3D Studio colour a model from a table: the toolkit's `view3d.color` output as a JSON of GlobalIds and colours that their viewers read. (recombine)
27. Open Calc Studio (cost) and Open Heatloss Studio (ISSO 51) need quantities; a toolkit graph that produces a clean quantity table per storey becomes their input, with the run record as the derivation. (what if the toolkit were a supplier, not an app)
28. Their Dutch IFC template (`inb-template`, NEN 47 materials and profiles) as a reference table in a `check.required` graph: "which elements use a material not in the template". (borrow from standards bodies: a controlled vocabulary)
29. `building.py` (their Python building generator, 45 stars) makes synthetic models; the toolkit's benchmark needs public models with known answers. Generated models give ground truth by construction. (borrow from testing: seeded generators, like `@bim-open-viewer/synthetic`)
30. Script nodes (workflow 4, TKT-162 asks which language) in Python would let their community's IfcOpenShell snippets become nodes with catalog entries. One argument for Python in that decision. (what if the language choice were made by who writes the scripts)

### Events, teaching, and community

31. A workshop repository in the shape of their Delft one: clone, start `claude`, ask questions about a public model through the toolkit's servers, and save a notebook in `session-1/<name>/`. Their template already proved the format to a room. (borrow from the Delft repository)
32. Their Delft `session-1/` folder holds no participant work; ours would collect each participant's saved notebook as the deliverable, so the workshop leaves evidence behind. (invert: the output is the session, not a tool)
33. Offer a talk or workshop at their next event, with the benchmark result as the opening slide. (what if the benchmark were the pitch)
34. Student internships are one of their four pillars; a student project could port a node pack to Python, or write the IFCX mapping. (outside software: apprenticeship)
35. Post in their WhatsApp community or feedback site only after something installs in one step; a broken first install costs more goodwill than no post. (what if the first impression were the only one)
36. Co-maintain one package with them instead of shipping a parallel one: an "IFC answers" section inside the IFC package that points at `bimopen-ifc` for questions about existing models. (economics: one shop instead of two)
37. A Dutch-language Ask guide, since most of their READMEs and their audience are Dutch. The Ask box would then answer "hoeveel deuren per verdieping" with the same graphs. (extreme: a second language)

### Benchmarks and evidence

38. A third benchmark arm (workflow 5): the same questions, the same model, with only the raw files, a shell, and the foundation's IFC skill package. It answers the question the foundation would ask: do knowledge skills close the gap, or does a tool server matter? (what if a competitor did it by hand)
39. Co-publish the result on both sides, with transcripts, so the foundation has a number for its packages and the toolkit has an outside audience for its benchmark. (economics: prices as signals)
40. A per-skill ablation: run the bare arm once per IFC sub-skill and report which skill moved correctness. A contribution to their package as data, not code. (borrow from science: ablation studies)
41. Use their IDS files as benchmark tasks: "does this model meet RVB BIM norm v1.1, and which elements fail". A task with a public, external answer key. (recombine 22 and 38)

### Far-fetched, minimal, and deliberately bad

42. The toolkit becomes an OpenAEC project: repositories moved into their organisation, Dutch README, their style book. Gains a community; loses the owner's control of priorities and the `ara3d` name. (deliberately far)
43. Their Studios each grow an MCP server (the OSArch thread says this is planned); the toolkit's flow MCP server orchestrates them as nodes: a `studio.heatloss` node that calls Open Heatloss Studio's MCP. (extreme: every app a node)
44. A skill package generated by their seven-phase method with the toolkit as the subject: their agents research `docs/` and write `bimopen-*` skills; the toolkit gets a second, independent description of itself, and the gaps show where the docs are unclear. (what if someone else described us)
45. Ten lines: add `license: MIT` and a `compatibility` line to the two SKILL.md files, then submit the repository to skills.sh. Nothing else. (extreme: ten lines)
46. Deliberately bad: copy all 177 of their skills into `.claude/skills/` so the toolkit "knows everything about AEC". Its inversion: ship zero third-party skills, and let the benchmark decide which, if any, earn a place, one at a time, each with a measured gain. (bad idea, then inverted)
47. Do nothing: users who want both install their packages and the toolkit separately. Document the two install lines and count how many steps it is. (what if we did nothing)

## Tensions

- **Knowledge skills against tool skills.** Their packages teach Claude to write code against a library and install by copying a folder. The toolkit's skills are instructions for MCP servers that need a .NET build (`.mcp.json` points at DLLs under `artifacts/`). Publishing the toolkit's skills the way they publish theirs gives a user a skill that names tools they do not have; real "one install" needs a plugin that carries the servers.
- **Distribution reach against token cost.** Their whole skills.sh presence is 304 installs, so the reach is modest; bundling their packages costs about 100 tokens of metadata per skill at every session start, and the brief sells low token cost. Any bundle has to earn its tokens in the benchmark.
- **A partner that is still forming.** The foundation is "in formation" nine months after its planned founding date, the skill packages moved from its organisation to a company, and the Composer's registry no longer finds them. Depending on any one of their repositories means pinning by commit and expecting moves.
- **Which workflow it serves.** Ideas 1, 8, 10, and 25 serve workflow 1 (look, then install one thing); 5, 6, and 30 serve workflow 4 (extend with a script or a pack); 22, 23, and 26 serve workflow 3 (hand the answer to someone); 38 to 41 serve workflow 5 (measure it). Principle 9 says the first piece of work names one.

## Approaches

1. **Publish to their channels** (ideas 1, 3, 4, 8, 9, 17, 45): make the two skills conform, add `license` and `compatibility`, list the repository on skills.sh, and open pull requests to the Composer. Good for being found by the people who already install AEC skills, at a cost of hours; fails when a user installs the skills without the servers and the first question errors, which damages workflow 1 more than silence.
2. **One plugin that carries everything** (10, 11, 12, 15, 16): a Claude Code plugin with the two MCP servers as built binaries, the toolkit's skills, a routing skill, and a commit-pinned subset of their IFC package. Good for workflow 1's Done line (one command, then a correct answer about a public model); fails on shipping .NET binaries for each platform and on the token cost if the bundled subset is not measured.
3. **Benchmark partnership** (38, 39, 40, 41, 20): add a third arm that uses their IFC package, publish the three-arm report, and offer them the per-skill ablation. Good for workflow 5 and for giving the foundation something it cannot produce itself; fails if the committed question set (TKT-8) is not ready, or if the foundation does not engage, though the arm is still useful alone.
4. **Tool interoperation through files** (22, 23, 24, 26, 27, 28): IDS parity, BCF export, IFCX mapping, colour tables for their viewers, quantity tables for their calculators. Good for workflow 3 and for Dutch practices that use their validator; fails on the moving targets of a young project, and on Dutch-specific standards that few other users share.
5. **Community and teaching** (31, 32, 33, 34, 36, 37): a workshop repository, a talk, a student project, a co-maintained package. Good for reach and for honest feedback from people who write no code; fails on the owner's time, which principle 9 guards, and on a community whose main channel is a WhatsApp group.

## Recommendation (soft; the user asked for evaluation afterwards)

Approach 3 first, with the small half of approach 1 alongside. The benchmark arm that uses their IFC package (idea 38) is the cheapest piece that serves a named workflow (5), produces a number nobody else has, and gives the foundation a reason to answer an email; it needs only the committed question set and a third configuration of the bare arm. In the same pass, add `license` and `compatibility` to the two SKILL.md files (idea 45) so they are publishable, but do not announce them on skills.sh or the Composer until the plugin of approach 2 exists, because the tension that decides this is knowledge skills against tool skills: a folder without its servers is a broken first install. Approach 2 is then the workflow 1 project, with the bundle limited to whatever third-party skills the benchmark showed to help. Idea 9 (fix their registry) is a good low-cost introduction whenever contact starts.

## Decisions for the user

- Which workflow does the first OpenAEC work serve? Default: workflow 5 (the third benchmark arm), then workflow 1 (the plugin).
- Bundle any of their packages in the toolkit's install? Default: none until the benchmark shows a gain; then a commit-pinned subset, never whole packages.
- Publish the toolkit's skills on skills.sh and in the Composer before a plugin carries the servers? Default: no; prepare the frontmatter now, list them when the plugin exists.
- Contact the foundation, and through which person? Default: after the three-arm report exists, open an issue or pull request on `OpenAEC-Workspace-Composer` (idea 9) and mention the report; Freek Heijting for the skill packages, Maarten Vroegindeweij for the foundation.
- Follow their naming pattern (`bimopen-impl-...`) or keep `bim-flow` and `ifc-ask`? Default: keep the current names, since the Ask box and the docs refer to them; revisit only if the toolkit's skills are listed inside their Composer.
