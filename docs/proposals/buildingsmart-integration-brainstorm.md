# buildingSMART integration: brainstorm

> Brainstorm, 2026-10-10. A wide, unjudged list of ways BIM Open Toolkit could connect to buildingSMART International's standards and open-source work (https://github.com/buildingSMART), followed by the tensions, five grouped approaches, and a soft recommendation. Nothing here is decided; the next step is to pick ideas and evaluate them (the `platonic:investigate` skill for a spike, `platonic:no-new-wheels` for reuse). Facts about buildingSMART were checked on 2026-10-10 against the GitHub repositories (README and LICENSE files, file trees counted from the repository archives), buildingsmart.github.io/validate, the bSDD documentation, and the pages listed under Sources, and are marked **docs**; everything else is **inferred**. Several buildingsmart.org pages refused automated fetches (HTTP 403); facts that rest only on a search-engine excerpt of such a page say so.
>
> Earlier work in this repository: `docs/proposals/ids-reuse.md` (2026-09-27) settled how to read IDS: parse with `Xbim.InformationSpecifications` (CDDL-1.0, referenced unmodified), audit with `ids-lib` (MIT), build the evaluator over BOS tables because every existing evaluator walks an IFC object model, reject xbim's validator (AGPL-3.0), and use IfcOpenShell's `ifctester` (LGPL-3.0) only as an external parity reference. TKT-50 (IDS check for the NRC analytics) carries that plan; as of 2026-10-03 only the reuse check and a 206-line skeleton (`deps/bim-open-data/src/data/Ara3D.Ids/`: `BosModel.cs`, `IdsFile.cs`, `Verdict.cs`, no evaluator, no tests) exist, and `samples/nrc/ids/` is empty. TKT-171 (BCF 3.0 export from a check's failing rows) is open, and an uncommitted writer sits in `deps/bim-open-data/src/data/Ara3D.BimOpenSchema.IO.Bcf/` (`BcfWriter.cs`, `BcfIssueTable.cs`, `BcfCamera.cs`). `docs/CONTRIBUTIONS.md` calls IFC "the source of truth", says "an IFCX file could be a BOS source", and lists IDS support as in progress.

## What buildingSMART is, in the terms this repository uses

- **The organisation on GitHub.** 24 public repositories under `buildingSMART`. Licences split in two: the specifications (`IFC4.x-development`, `IDS`, `BCF-XML`, `BCF-API`) are CC BY-ND 4.0, which allows redistribution with credit but no derivatives; the tooling (`validate`, `ifc-gherkin-rules`, `ifc-validation-data-model`, `IDS-Audit-tool`, `bSDD`) is MIT. `IFC5-development` has no licence file; its README says "Do not create derivatives of these examples" and that the viewer source is MIT. **docs**
- **IFC 4.3.** `IFC4.x-development` holds IFC4.3.2.0, the version ISO approved (ISO 16739-1:2024); builds are published in `Standards-builds` and as HTML at standards.buildingsmart.org/IFC/DEV/IFC4_3/. **docs** The toolkit reads IFC through web-ifc into BOS (BIM Open Schema, the toolkit's columnar entity, parameter, and relation tables) and writes property sets back byte-exact (`Ara3D.Ifc.Editing`, `sink.writePsets`).
- **IFC5 and IFCX.** Alpha. An `.ifcx` file is JSON with a `header` (`"ifcxVersion": "ifcx_alpha"`), `imports` (URIs on ifcx.dev, for example `https://ifcx.dev/@standards.buildingsmart.org/ifc/core/ifc@v5a.ifcx` and `https://ifcx.dev/@openusd.org/usd@v1.ifcx`), `schemas`, and `data`: a list of entries keyed by `path` (a UUID), each with `children`, `inherits`, or `attributes`. Attribute names are namespaced: `bsi::ifc::class`, `bsi::ifc::prop::FireRating`, `bsi::ifc::material`, `usd::usdgeom::mesh`, `usd::xformop`, `nlsfb::class`. A second file adds a layer: `hello-wall-add-fire-rating-30.ifcx` is 30 lines that set one attribute on one path. The repository has 13 example folders (Hello Wall, Tekla House, ACCA Building, Railway, Road, Tunnel Excavation, Point Cloud, and others), a schema written in TypeSpec, and a live viewer. **docs** buildingSMART announced on 2026-08-26 that the "IFCX Core & Modularisation" project plan passed its approval phase, developed "in coordination with ISO/CEN" **docs** (search excerpt; the page returned 403). An OSArch commenter on that announcement estimated "5 to 10 years" before IFCX is usable for real work. **docs** (opinion, not buildingSMART's)
- **IDS (Information Delivery Specification).** An XML format, defined by an XSD, that states which elements must carry which classes, attributes, properties, materials, and parts; version 1.0 became a final buildingSMART standard in June 2024. **docs** The `IDS` repository's `Documentation/ImplementersDocumentation/TestCases` holds 334 `.ids` files and 334 `.ifc` files (counted on the `development` branch), the pairs implementers test against. **docs** `IDS-Audit-tool` (MIT) checks an IDS file's validity. **docs** UCM (Use Case Management, ucm.buildingsmart.org) publishes use cases with their exchange requirements "in the machine-interpretable Information Delivery Specification (IDS) format". **docs**
- **The validation service** (validate.buildingsmart.org). Free. Checks STEP syntax, IFC schema (attributes, inverses, WHERE rules, global rules), normative rules (implementer agreements, which are ratified, and informal propositions, which are mandatory but not ratified), and industry practices, which only warn; the bSDD check is "disabled" since version 0.6.6. Accepts IFC2X3, IFC4, and IFC4X3_ADD2, as unzipped `.ifc` files of at most 256 MB. **docs** The rules live in `ifc-gherkin-rules` (MIT): Gherkin `.feature` files run by Python `behave` over IfcOpenShell, each coded as a three-letter functional part and three digits (`ALB001`, `GEM900`). There are 104 feature files in 34 functional parts (ALB alignment 14, ALS 12, GEM geometry 11, GRF georeferencing 9, SPS spatial structure 8, IFC 6, PJS project 5, BLT built elements 4, and 26 smaller parts); 76 are tagged implementer agreement, 11 informal proposition, 16 industry practice, and 9 disabled. Outcomes are pass, fail, or N/A (not applicable), and industry practices give warnings instead of failures. **docs** (counts from the archive of `main` on 2026-10-10) The service has a REST API (`/api/v1/validationrequest`, `/validationtask`, `/validationoutcome`) that needs a token issued by email from validate@buildingsmart.org; a forum thread asks for it to be opened to the public. **docs** The whole service runs locally under Docker Compose (PostgreSQL, Redis, Django, a Celery worker, React). **docs**
- **Certification.** Software certification has export and import parts; its scorecards are built from anonymous metrics of files uploaded to the validation service. **docs** (search excerpt of the certification page, which returned 403) A funded plan adds digital certificates for files that pass validation. **docs** (search excerpt)
- **bSDD (buildingSMART Data Dictionary).** A hosted set of interlinked dictionaries (classes, properties, allowed values, units, translations) with REST and GraphQL at api.bsdd.buildingsmart.org; most read methods are anonymous, "secured methods" need OAuth2 through Azure AD B2C and a requested client id, and clients should name themselves in `User-Agent`. **docs** Each dictionary carries its own `License` and `LicenseUrl` (SPDX identifiers recommended), so reuse rights differ per dictionary. A class has `ClassType`, `ClassProperties`, `ClassRelations`, and `RelatedIfcEntityNamesList`; a property has `DataType`, `AllowedValues`, and `Units`. **docs** In IFC a bSDD class is referenced through `IfcClassification`, `IfcClassificationReference`, and `IfcRelAssociatesClassification`. **docs** (search excerpt)
- **BCF (BIM Collaboration Format).** BCF-XML 3.0 is a zip with `bcf.version`, `extensions.xml`, optional `project.bcfp` and `documents.xml`, and one folder per topic holding `markup.bcf`, `.bcfv` viewpoints, and snapshots; elements are named by IfcGuid, with `AuthoringToolId` as a fallback; viewpoints never change after creation. **docs** BCF API 3.0 is a REST service on the openCDE Foundation API 1.1, which supplies OAuth2 authentication, a versions endpoint, and a user endpoint; the Documents API 1.0 shares that foundation. **docs** `BCF-API` was last pushed 2025-06-16 and `OpenCDE-API` in 2022. **docs**
- **Sample files.** `buildingSMART/Sample-Test-Files` now redirects to `Certification-datasets`: 35 IFC files in three schema folders (IFC 2x3 TC1, IFC 4 ADD2 TC1, IFC 4.3 ADD2), CC BY 4.0. The earlier community content moved to `buildingsmart-community/Community-Sample-Test-Files` (CC BY 4.0, IFC, BCF, and IDS samples), whose README says most files "do not pass validity check on the validation service". **docs** TKT-144 (which sample models may be redistributed) still cites the old name.
- **Other serialisations.** ifcJSON (`buildingsmart-community/ifcJSON`, MIT) is a JSON form of IFC4 aimed at round-trip with STEP; it is a community project, not a standard. **docs**
- **AI.** No buildingSMART working group, position paper, or rule on AI or LLMs was found. **inferred** (searched 2026-10-10) The Tokyo summit (6 to 8 October 2026) lists AI among its topics, and the board vice chair said in a 2025 interview that AI-ready building data "has to be reliable. That means quality checks, regulation, and human oversight." **docs** That stance matches the toolkit's principles 3 (honest absence) and 4 (runs are the evidence). **inferred**

## Brainstorm

Goal: find where buildingSMART's standards and services fit the toolkit so that a person who already writes IDS files, runs the validation service, uses bSDD, or exchanges BCF gets something they cannot get today (asking Claude, a replayable graph, a picture, a benchmark number), and the toolkit gains a shared rule language, a vocabulary, an issue channel, public test data, and standing, without giving up its principles (one edit path, nothing writes until Run, honest absence, runs as evidence, tables as the currency).

Ideas, grouped by standard. Tags name the prompt that produced the idea.

### IDS as the rule language

1. A `check.ids` node: an IDS file as a parameter, the BOS tables in, the standard verdict table out (`verdict`, `checkId`, `checkTitle`, `citation`), one `checkId` per IDS specification. (extends `check.rule` and `check.required` in `BimOpenFlow.Nodes.Compliance` and the `Ara3D.Ids` skeleton; this is TKT-50's second half)
2. Compile each IDS facet to a SQL predicate over the BOS parameter tables, so a whole IDS runs as one DuckDB query on a model of Snowdon's size (about 450,000 instances) instead of an element-by-element walk. (borrow from databases: query compilation)
3. Open an IDS as a graph: each specification becomes a `check.rule` node a person can read, rewire, and tighten; the graph exports back to IDS while it stays inside the IDS subset. (what if the rule file were the graph; principle 1, one edit path)
4. Claude writes the IDS from a sentence ("every door needs `FireRating` in `Pset_DoorCommon`"), audits it with `ids-lib`, runs it, and shows the failing doors in 3D. A BIM manager who has never seen the XSD gets a valid IDS. (what if a person who writes no code had to author an IDS)
5. Infer an IDS from a model: profile parameter coverage with `bim.paramCoverage` and draft the IDS this model already passes, as the starting requirement set for the next phase. (invert: requirements from data)
6. A facet the evaluator cannot evaluate yields InfoNotAvailable with a warning, never Pass, and the report counts them. Other checkers stay silent here. (what if the evaluator were incomplete; principle 3)
7. A parity score: run the evaluator over all 334 test-case pairs in `IDS/Documentation/ImplementersDocumentation/TestCases` and publish the pass rate per facet, the number an IDS author asks first. (extreme: every test case)
8. Explanation columns: for each failure, the facet that failed, the expected value, and the value found ("expected R60, found R30"), peekable on the wire. (principle 8, it explains itself)
9. An IDS diff: two IDS files in, a table of added, removed, loosened, and tightened requirements, so a client's revision is readable. (borrow from law: a redline of a contract)
10. UCM use cases as a source: pick a use case, load its IDS, run it. The exchange requirement and the check share one URL. (what if it already existed)
11. IDS over non-IFC models: because evaluation reads BOS tables, the same IDS checks a Revit-exported BOS file, which no IFC-based checker can do. (what if IFC were forbidden)

### The validation service and its rules

12. A `check.gherkin` node that shells out to `ifc-gherkin-rules` (pytest or behave over IfcOpenShell) on the source IFC and returns the outcomes as a verdict table keyed by rule code. MIT, so it can ship. (extends the verdict-table shape; the parity runner in `tests/data/Ara3D.Ids.Tests/parity/run-ifctester.py` already shells out to Python)
13. Port the rules that are plain data questions to SQL over BOS: project definition (PJS), spatial structure (SPS), georeferencing (GRF), quantities (QTY), keeping the rule code as `checkId`. Geometry rules (GEM, ALB) stay with IfcOpenShell. (borrow from compilers: retargeting a front end)
14. A `bsi.validate` effect node: upload to the service's REST API inside a Run (an upload sends the model to a third party, so it is gated like a write), poll, and return outcomes. Needs a token. (what if somebody else ran it)
15. A validation gate in the IFC MCP server: on `ifc_open`, run syntax, schema, and a few gherkin rules, and attach the failures to every later answer ("this file fails SPS rules; storey counts may be wrong"). (what if the model were broken)
16. Read a validation report the user already has: their outcome export in, failing rules joined to elements by GlobalId, coloured with `view3d.color`. Claude explains each rule code in plain words. (recombine: report plus 3D)
17. Fix what can be fixed: for industry-practice warnings that are a missing or wrong property, propose a `sink.writePsets` patch, apply it byte-exact inside a Run, and revalidate. No other tool in the validation workflow edits the original file while leaving every other byte unchanged. (what if we kept the one thing we are uniquely good at)
18. A NotApplicable verdict: gherkin's N/A means "the rule does not apply", the toolkit's InfoNotAvailable means "the data is missing". A fifth verdict, ranked below Pass in `check.rollup`, keeps the two apart. (extends the verdict enum in `BimOpenFlow.Nodes.Compliance`)
19. Contribute rules back: a toolkit graph that agrees with the service on the test files becomes a proposed `.feature` file with its unit IFC files, a pull request to `ifc-gherkin-rules`. (invert: the toolkit as a source of rules)
20. A self-hosted validation service beside the studio, for models that cannot leave the office: one Docker Compose file, no token. (economics: confidentiality as the price)
21. Agreement as a benchmark: run the toolkit's ported rules and the service on the same files and report the agreement rate per rule; disagreements become tickets on one side or the other. (borrow from biology: redundancy)

### bSDD as the vocabulary

22. `bsdd.dictionary`, `bsdd.classes`, and `bsdd.properties` source nodes: a dictionary URI in, tables of classes, properties, allowed values, and units out, cached by dictionary version. Anonymous REST, so no account. (extends the table sources `json.read` and `duck.source`; pure, keyed like `bos.load`)
23. bSDD in live parameter suggestions: when a node asks for a property name or a value, the suggestions endpoint offers the bSDD names and allowed values for the element's class. (extends live parameter suggestions, `docs/proposals/live-param-suggestions.md`)
24. Classify elements against a bSDD dictionary (Uniclass, NL-SfB, ETIM, or a national one) from IFC class, type name, and properties; Claude proposes, a `check.rule` confirms, a person approves. (recombine `bim.classifyRooms` with bSDD)
25. Write the classification back: `IfcClassificationReference` with the bSDD URI, through the byte-exact editor, so the classified IFC differs from the original only by the added lines. (extends `sink.writePsets` and `Ara3D.Ifc.Editing`)
26. Drive the Harmonizer from bSDD: `CategoryMappings.cs` and `ParameterMappings.cs` in `Ara3D.BimOpenSchema.Harmonizer` read `RelatedIfcEntityNamesList` and `ClassRelations` instead of hand-written maps. (extends an existing abstraction)
27. The bSDD check the validation service disabled: compare each property's value with bSDD `AllowedValues`, `DataType`, and `Units`, as a verdict table. (what if the obvious provider stopped)
28. Units from bSDD: a property's declared units drive the unit conversion in `UnitConversion.cs`, so a value read as 2400 is labelled millimetres from the dictionary, not from a guess. (principle 3, no size read from a name)
29. Labels in the reader's language from bSDD translations, in charts, tables, and reports. (outside software: localisation)
30. Publish the toolkit's own vocabulary to bSDD: the BOS relation kinds (`PartOf`, `ContainedIn`, `HostedBy`, `BoundedBy`) and its derived measures as a small dictionary, so other tools can cite them. (invert: consumer becomes publisher)
31. IDS with bSDD URIs: Claude writes IDS whose classification and property facets carry `uri` attributes pointing at bSDD, so the requirement and the definition travel together. (recombine 4 and 22)

### BCF as the issue channel

32. A `sink.bcf` effect node: a verdict table in, a BCF 3.0 file out, one topic per failing element or per check. (extends the TKT-171 writer and the `sink.*` nodes in `BimOpenFlow.Nodes.Effects`)
33. Snapshots from the 3D pane: each viewpoint's snapshot is rendered by the pane's capture with the failing elements coloured, so every issue carries a picture. (recombine: `view3d.color` plus capture plus BCF)
34. `bcf.read`: topics, comments, statuses, and component GlobalIds as a table, joined to elements: "which storeys collect open issues", "which check produces the most rejected issues". (invert: sink becomes source)
35. Close the loop: read back a BCF that came through Solibri or BIMcollab, rerun the checks on the new model, and mark topics whose elements now pass. (extreme: a thousand issues across ten revisions)
36. The run record inside the issue: `documents.xml` references the evidence package, so whoever opens the issue can replay the check that raised it. (borrow from libraries: provenance travels with the item; principle 4)
37. A BCF API client: publish topics to a CDE that implements openCDE BCF API 3.0, with OAuth2 from the Foundation API, inside a Run. (what if nobody opened the toolkit)

### IFC5 and IFCX as a future input

38. An `ifcx.load` node: compose the layers, then map `path` to entity, namespaced `attributes` to parameters (namespace as the parameter's group), and `children` to `PartOf` and `ContainedIn` relations. The output is the same three BOS tables `bos.load` gives. (extends `bos.load`; `json.read` already parses JSON)
39. Layers as a time axis: load each IFCX layer separately and diff them, so "who added which property" is a table. (what if the format were the history)
40. Results as a layer: write verdicts or bSDD classes as an `add-verdicts.ifcx` layer over the base file, the IFCX equivalent of byte-exact write-back, with no edit to the original. (invert: the sink becomes a layer)
41. One geometry path: IFCX geometry is `usd::usdgeom::mesh`, and the toolkit already exports USD (`Ara3D.BimOpenSchema.IO.Usd`, TKT-173). Read and write meshes through the same code. (recombine)
42. A round-trip test over the 13 IFC5 example folders, several of which ship an `.ifc` beside the `.ifcx`: load both, compare the BOS tables, report every difference. A free conformance check for the converter and for the examples. (extreme: every example)
43. Take a seat in the IFC5 work: the toolkit's columnar view as evidence of what analytics consumers need from IFCX, raised as issues on `IFC5-development`. (outside software: standards politics)

### Test data, benchmarks, and standing

44. `Certification-datasets` (35 IFC files, CC BY 4.0) as the toolkit's public sample set for workflow 1, which settles part of TKT-144 for files buildingSMART itself licenses. (what if the problem moved to someone else)
45. A parse ratchet: open every file in `Certification-datasets`, the community samples, and the 334 IDS test-case IFC files through `bimopen-ifc`; count load, meshing, and BOS conversion failures, and let the count only fall. (extreme: every public file)
46. A benchmark arm built from buildingSMART's own answers: questions over `Certification-datasets` whose ground truth comes from the validation service and `ifctester`, run with and without the toolkit (workflow 5). (recombine 7, 21, and workflow 5)
47. Propose that benchmark to buildingSMART as an open "AI over IFC" test set with the toolkit as the first entry. buildingSMART has no AI position yet; a test set fits its stance that data must be checked. (what if it were a convention instead of a tool)
48. A `bimopen-bsi` MCP server beside `bimopen-ifc` and `bimopenflow-duckdb`: `ids_audit`, `ids_check`, `bsdd_search`, `bsdd_class`, `bcf_write`, `gherkin_check`. Same shape as the existing servers in `.mcp.json`. (extends the two MCP servers)
49. An openBIM skill shipped with the one-command install: IDS facets, bSDD lookup, and BCF in Claude's words, so a question that names IDS works on the first try (workflow 1). (extends `.claude/skills/ifc-ask/`)
50. Get listed: add the toolkit to the self-managed software implementations list on technical.buildingsmart.org under IDS checking, bSDD read, and BCF export, once each passes its parity test. (economics: a free distribution channel)
51. Certification as a goal, not a feature: IFC import certification is for software that reads IFC; ask whether a read-only analysis tool qualifies, and what IDS checking would need. (far-fetched)
52. An openBIM Awards entry: an IDS-in, BCF-out session recorded live in Claude Code, with the benchmark score. (outside software: competitions)

### Minimal and deliberately bad

53. Ten lines: run `ifctester` with its JSON reporter, read the report with `json.read`, colour the failures. No evaluator of our own. (extreme: ten lines)
54. Deliberately bad: adopt IfcOpenShell's object model inside the host and run every buildingSMART tool natively. Its inversion: no IFC object model in the host at all; buildingSMART standards meet the toolkit only at its edges, IDS and bSDD in, BCF and IFCX layers out, BOS tables in between. (bad idea, then inverted)
55. Do nothing: users run the validation service and an IDS checker themselves and paste the results to Claude. Document that path and count its steps, as the bare arm of the comparison. (what if we did nothing)

## Tensions

- **Reuse the reference checker or build over BOS.** `ifctester` and the gherkin rules define correct behaviour and run on IfcOpenShell; reusing them costs a Python dependency and an IFC object model beside web-ifc. An evaluator over BOS is fast, works on non-IFC sources, and fits "tables are the currency", but every gap between BOS and IFC (attributes such as `PredefinedType`, materials, `partOf` relations) becomes a parity failure to chase.
- **Licences.** The specifications, the IDS test cases, and the BCF schemas are CC BY-ND 4.0, and the IFC5 examples ask for no derivatives. The toolkit can implement the standards and test against the files unmodified, but should fetch them by script like `data/` rather than commit trimmed or edited copies. bSDD dictionaries each carry their own licence. The tooling repositories are MIT and free to ship.
- **Verdict vocabularies.** Gherkin gives pass, fail, N/A, and warning; IDS gives pass and fail per requirement with optional and prohibited cardinality; the toolkit gives Pass, Fail, NeedsReview, and InfoNotAvailable. Mapping N/A onto InfoNotAvailable would blur "does not apply" with "data missing" and break principle 3.
- **Maturity.** IDS 1.0 and BCF 3.0 are final, and bSDD is in production. IFCX is alpha with a project plan approved six weeks ago; the validation API is gated by token. Work on the stable standards pays now; IFCX work may be rewritten.

## Approaches

1. **IDS end to end** (ideas 1, 2, 4, 6, 7, 8, 31): finish TKT-50's evaluator over BOS, score it on the 334 IDS test-case pairs, add `check.ids` and an MCP tool, and let Claude author IDS. Good for workflows 2 and 5 and for every IDS author, since IDS is the shared rule language; fails if the IFC-to-BOS conversion drops attributes or relations that the test cases depend on, which would make parity a long tail.
2. **Issue loop** (32, 33, 34, 35, 36): verdicts out as BCF with snapshots and the run record, BCF back in as a table. Good for workflow 3, because BCF reaches Solibri, BIMcollab, and Revit users who never open the toolkit, and the TKT-171 writer exists; fails if the checks feeding it are not trusted, so it follows approach 1.
3. **Validation service as reference and benchmark** (12, 13, 15, 16, 21, 45, 46): run the gherkin rules locally, port the data rules to SQL, measure agreement, and gate the IFC MCP server on validity. Good for workflow 5 and for borrowing buildingSMART's authority as the answer key; fails on the Python and IfcOpenShell dependency in a Windows .NET host, and on geometry rules that only IfcOpenShell can evaluate.
4. **bSDD vocabulary** (22, 23, 24, 25, 26, 27, 28): read-only source nodes, suggestions, classification, and byte-exact write-back of classification references. Good for workflow 2 (Claude stops guessing property names) and cheap because the API is anonymous; fails on per-dictionary licences and on dictionaries too thin to classify from.
5. **IFCX early** (38, 39, 40, 41, 42, 43): `ifcx.load`, verdicts as layers, the round-trip test over the 13 examples. Good for positioning and for a voice in the IFC5 work; fails on alpha churn and the "no derivatives" request on the examples.

## Recommendation (soft; the user asked for evaluation afterwards)

Approach 1, then approach 2. IDS is the standard buildingSMART's users already write, it is final, and TKT-50 has its reuse decision made; the 334 test-case pairs turn "does the toolkit check IDS correctly" into a number, which is what an IDS author and principle 9 both ask for. The one fact that decides the cost is whether the IFC-to-BOS conversion carries what the test cases test (entity attributes, `PredefinedType`, materials, `partOf` and classification relations): a one-day spike that converts the 334 test IFC files and counts the facets with no source column settles it. If the gaps are small, `check.ids` feeding the TKT-171 BCF writer gives the most common openBIM loop, IDS in and BCF out, with a picture per issue and a replayable run behind each. bSDD source nodes (approach 4) are the cheapest third step. IFCX should get the round-trip spike (idea 42) and no node until the format leaves alpha.

## Decisions for the user

- Which workflow does the first buildingSMART work serve? Default: workflow 2 (Claude checks a model against an IDS), with workflow 3 (results as BCF) second.
- Build the IDS evaluator over BOS (the plan in `ids-reuse.md`) or call `ifctester` (idea 53)? Default: over BOS, with `ifctester` as the parity reference, as already decided; revisit only if the spike shows large conversion gaps.
- Add a NotApplicable verdict to the compliance pack (idea 18)? Default: yes, before any gherkin outcome is ingested, filed as its own ticket.
- Request a validation-service API token, or run the service locally? Default: run the rules locally; no model leaves the machine.
- Commit buildingSMART's test files? Default: no; fetch them at a pinned commit by script, cite the licence, and commit only results.
- Point TKT-144 at `Certification-datasets` as the CC BY 4.0 public sample set? Default: yes, after reading each file's header for its origin.
