# STEP mesher in Plato, version 2: independent tracks merged in waves

Status: in progress
Ticket: TKT-323

Written 2026-10-18 by the supervising session, at the owner's request: plan the remaining mesher work so it runs in parallel, keeps each piece of work independent, merges at the end, and does not slow down as more tracks are added; the coordination learns as it goes. Owner decisions the same day: plain 32-bit floats (the `gpu32` profile) until the 64-bit Number profile lands, which gets its own track; no exact predicates; work unattended. It replaces the track table of `docs/plans/step-mesher-parallel.md` (version 1, whose rules and log stay in force where this file does not override them).

## Why version 1 slowed down as work grew

Evidence from 2026-10-18, wave 1 of version 1:

- **One program, one failure for everyone.** The library compiles as one program. One agent's missing semicolon made the shared warm checker report "0 laws, 0 type errors" for every agent until it was fixed (TKT-337).
- **Shared files between fences.** Of the cross-fence requests the supervisor routed by hand, at least eight came from functions or laws that two tracks both needed: `CopiesInside`, `ClosestParameter`, two witnesses, two layer 7 check files, the derivative tolerance, the cone's area sign.
- **One mailbox.** Every request went through one supervisor session, which hit the app's limit of ten messages between sessions once and had to wait for the owner.
- **Ordered steps.** Steps C and F waited on each other only because the build order said so, not because the code did.

## Design

1. **A staging folder per track.** Each track works only in `sandbox/step-mesh-staging/<track>/`, outside the library tree, adding new files. Its checks compile the library plus its own folder, so a broken track breaks only itself. Rules and naming: `sandbox/step-mesh-staging/README.md`.
2. **Merge by wiring, not by splicing.** A body for a declared function is staged as `<Name>Body`; a replacement gets a new name. At merge the supervisor moves the files into the layer they belong to and makes the one-line wiring edits each track lists under "Merge instructions" in its `TRACK.md`. No merge splices lines inside a function two tracks both wrote.
3. **Additions never wait; changes wait for the wave.** A track adds a type or a function in a new file in its staging folder whenever its code needs one, without a request: an addition breaks no other track. Only changing or removing a type or signature the library already has waits for the wave boundary, through a contract request. (Until 2026-10-19 this rule froze additions too; seven tracks merged under it and none added a type. Now in platonic `CHUNKING.md`.)
4. **Status in files, not messages.** Each track keeps `TRACK.md` (status, merge instructions, contract and cross-track requests, findings, durations, lessons). Requests to another track are written there; the supervisor collects them at merge. Messages are only for being blocked.
5. **Floats now, doubles later.** Every check ran under `gpu32` until TKT-315 merged on 2026-10-19; since then the default is `cpu64`. When TKT-315 lands, the supervisor merges it alone, switches the default profile to `cpu64`, and reruns the full sweep; any law whose verdict changes is a finding.
6. **Checks stay warm per track.** `tools/plato_laws.py --staging <folder>` runs on the warm server; TKT-344 makes the server keep one compiled program per folder set, so tracks stop evicting each other.

## Wave 2: chunks, not tracks

Written 2026-10-19 after the owner asked for significantly finer work. Wave 1's unit of work was the ticket: seven rows, no chunks under them, tracks of 2 hours to 2 days that each merged once, and every merge paid a 57 to 120 minute sweep. From here on (platonic `CHUNKING.md`, `PLANNING.md` step 7, `TESTING.md`, and the parallel-wave skill carry the same rules, written from this wave's evidence):

- **The chunk is the unit of work and of merge.** Every row below is one commit, with its own fence, test, and an expected duration of at most two hours. A builder marks a chunk ready the moment it is green, commits it, and takes its next chunk from the table. Green work held for a bigger merge is a defect.
- **One chunk per brief.** A session that owns a staging folder is told its first chunk and the rule "then take the next chunk with your owner name, in table order". The supervisor compares each session's last commit time with the chunk's expected duration; past it with no commit is a stall to check.
- **Additions never wait.** A new type, function, law or witness goes in a new file in the staging folder at once (design item 3). Only a change to an existing type or signature is a contract request, and such a chunk is merged alone by the supervisor.
- **Merge check under ten minutes.** Until the compiled runner (TKT-354) and the affected-law filter (chunk I6) exist, a chunk merge runs only the laws its row names plus the laws of its layer's files, with `plato_laws.py` on the warm server; the full sweep against `verdicts-cpu64.tsv` runs once a day, or after every fifth merge, whichever comes first, and any verdict that changed is traced to the chunk that changed it.
- **The ledger counts chunks.** New columns: chunks merged, mean chunk wall time, and types added. A chunk that adds no type says in its `TRACK.md` entry what values it passes around and why none deserved one. `sandbox/step-brep-mesh/TYPE-CATALOG.md` (2026-10-19) lists the types and concepts a builder reaches for first: points by space, decided results, proof-carrying types, allowances with derivations, edits and repairs as data.

## Merge procedure (supervisor)

1. A chunk's owner marks it `ready: <id>` in its `TRACK.md` and commits it.
2. The supervisor moves its files into the right layer folders, renames `Law_<Track>_` laws, makes its wiring edits, and type-checks the whole library.
3. Merge check, under ten minutes: the laws the chunk's row names plus the laws of the files it touched, with `plato_laws.py`; once chunk I6 lands, the affected-law filter instead. A law that passed and no longer passes stops the merge; the chunk goes back with the evidence.
4. Commit the merge and the chunk's findings in `reviews/FINDINGS.md`.
5. Record the chunk in the ledger: id, claim-to-ready time against expected, types added.
6. Full sweep with `--report` and `--baseline` against `sandbox/step-brep-mesh/reviews/verdicts-cpu64.tsv` once a day or after every fifth merge; commit the new verdict file; trace each changed verdict to its chunk.
7. When a merge changes generated C# behaviour, announce it to the E owner, which regenerates once (chunk E1 and its successors).
