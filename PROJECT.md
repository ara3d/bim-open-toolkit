# BIM Open Toolkit: project brief

Written 2026-09-26 by an unattended session from the repository's documents, checked against the code by four independent readers, and amended the same day with the owner's eight findings from using the studio (`docs/CANDIDATE-WORK.md`, "Owner's findings"); `docs/CANDIDATE-WORK.md` lists the sources and the ideas gathered. A line ending `(unconfirmed)` rests on a proposal or an inference; the owner confirms or corrects it and removes the marker.

## Purpose

Building data is locked behind each authoring tool's API, and the exchange formats that exist were shaped for geometry handoff, not analysis. BIM Open Toolkit stores a model as plain tables (BIM Open Schema, BOS) and turns questions about those tables into small, inspectable, reproducible graphs (BimOpenFlow) that people and AI agents build the same way. It exists so that an analyst gets a schedule, a check, a chart, or a coloured model out of a building without a vendor's process, and so that an agent doing it for them produces evidence rather than a guess.

## Users

- **BIM analyst or manager** with a converted model and a question: a door schedule, rooms per storey, what is missing. Writes no code. Served today through the Snowdon DuckDB studio, once a developer has started it.
- **An agent acting for them**: Claude in the studio's Ask box, or in Claude Code through the two MCP (Model Context Protocol) servers, `bimopenflow-duckdb` and `bimopen-ifc`, and their skills. Needs a self-describing catalog, paged read-back, exploration that cannot write, and a run record to hand over.
- **Reviewer of the model in 3D**: category colours, sections, exploded views, plans, ghosting; picks an element and reads its property sets.
- **Developer or coding agent** extending the toolkit with a node pack, a pane, a viewer feature, or an MCP tool; the specified engine, its conformance suite, and the layering tests exist for them.
- **Compliance checker** applying one cited rule to a model and handing an official the offenders and a report whose numbers can be replayed.
- **Researcher** (the NRC paper; National Research Council Canada) reproducing its figures from one command and writing enrichment results back into a copy of the IFC (Industry Foundation Classes) file without disturbing any other byte.

## Workflows

1. **Start from a clean clone and answer a question about Snowdon.** Actor and trigger: an analyst, or a newcomer with the prerequisites installed, wants a door schedule, rooms per storey, or a missing-width list from the Snowdon model, or first wants to see the toolkit work at all. Today: the typed DuckDB comes from `run-samples.ps1 -Prepare` and `export-duckdb`, run by hand over the private BOS; `npm run duckdb:prepare` then seeds a store whose copies of the sample graphs carry a machine-local path in place of the `{DUCKDB}` placeholder; the host's default port and the editor's proxy disagree, two terminals are needed, and no page says which demos are supported, so a clean clone has not been shown to reproduce the demo. With this project: the Snowdon data is the seven discipline IFC files merged into one model with a correspondence table for storeys, grids, and spaces (TKT-30; GlobalId is not a key across the files), one documented command starts the host and the page, a start page lists the supported demos, and the same steps work on any machine. Done: on a fresh clone with no private files, the start command opens the tables-profile analyses with every node green and one chart from a template; with the private Snowdon files at the documented location and no hand edits, the documented prepare step and then `check-bim-flow-duckdb.mjs` pass with every node of every sample graph green and the database hash unchanged, and `/duckdb.html` shows 142 doors and 290 spaces. Cost of failure: every table, chart, and Ask demo over the real model works on one machine only, and a newcomer's first ten minutes go on ports.
2. **Ask in plain language and get a graph you can inspect.** Actor and trigger: an analyst who will not wire nodes types a question in the Ask box; a developer asks the same in Claude Code, about the Snowdon export or about an IFC file. Today: with an API key (the owner has since decided against the API: Claude is called through the Claude Code command line with Haiku at medium effort, TKT-45), the agent calls `describeDatabase`, one `editGraph` batch, `evaluate`, and `getResult`, and the finished graph opens in the editor (a graph built from Claude Code over MCP needs a reload); the host already prefers the Anthropic key when both are set, but every published number is gpt-5's (8 correct graphs, 2 honest answers without a graph, 0 wrong of 10), the ten questions exist only as prose, and nothing on the canvas says why a node is not ready. With this project: the ten questions and their expected answers are a committed file and Claude is measured on it; the agent knows the open graph and the selection without being told; every node shows its state and names the upstream cause, selecting a node lights the path that feeds it, and any wire can be peeked at for its rows and count; an agent's edits arrive selected, undoable, and reviewable in a panel that holds still while it answers. Done: `scripts/ask-bim-flow.mjs --file` over the committed set scores at least 8 correct and 0 wrong with Claude, transcript committed; `scripts/demo-bim-flow-mcp.mjs` exits 0 with 142 rows; the IFC ask answers the eight questions in `samples/nrc/questions.txt` to match `expected_answers.json`; hovering a wire of the built graph shows its row count. Cost of failure: the AI story is a demo that worked once, and people go back to hand-written SQL.
3. **Chart it and take it with you.** Actor and trigger: an analyst wants rooms per storey or elements per type as a chart, and an Excel or Parquet file for the next tool. Today: `chart.bar`, `chart.line`, and the export sinks exist, but the studio's right panel has no chart tab, and an export waits for a Run that only the HTTP API and the `createRun` MCP tool can create and that nothing outside the tests executes. With this project: a chart pane sits next to every Snowdon table, and a Run button in the editor writes the export with a run record. Done: a chart of rooms per storey (33 storeys with rooms) renders in the studio, and after Run an `.xlsx` exists on disk and is named in the run record. Cost of failure: "detailed analysis and charts" stays a screenshot of a table.
4. **See it in the building.** Actor and trigger: a reviewer wants Snowdon coloured by category, sectioned, exploded, and to pick an element for its property sets. Today: `/3d.html?analysis=snowdon-toolkit` renders 456,598 instances from an eleven-node recipe with a category legend, 5.2 to 5.8 s to the first frame as `scripts/profile-bim-flow-startup.mjs` measures it, no legend for value colourings, and none shared with other panes. With this project: the 3D pane opens inside the studio on the same graph and store, a coarse first frame ahead of the full load, one colour domain with a legend across panes, saved views, and selection linked between graph, table, and 3D. Done: a table node's value colours Snowdon in the studio, the four captures regenerate, the value legend is populated and matches the chart pane's, and the measured warm first frame is under 2 s in the startup log. Cost of failure: the most persuasive demo of graphs meeting visualisation feels slow and unfinished.
5. **Check a rule and hand over the evidence.** Actor and trigger: a compliance checker applies DC-W1 (door leaf width at least 850 mm) to a model. Today: `nrc-dc-w1-verdicts` gives 8 Pass and 6 Fail on the Duplex sample and colours the doors; the showcase graph adds `chart.bar` and `sink.report`; the report stays `EffectPending` because nothing outside the tests executes effects, and no node produces an evidence package although the `BimOpenFlow.Evidence` library can build one. With this project: a verdict pane with rollups and citations, a Run from the editor that pins the graph and input hashes, and a static report and an evidence package produced from that run. Done: after Run from the editor, `report.html` and an evidence package (a zip whose `manifest.json` lists a SHA-256 per member) exist on disk. Cost of failure: the NRC deliverable and the claim "evidence, not suggestion" have no artefact behind them.
6. **Reproduce the paper, including the write-back, with one command.** Actor and trigger: the owner or the researcher before a submission or a demo. Today: `npm run nrc:walkthrough` builds the host and both MCP servers and captures 10 Duplex and 6 Snowdon figures with transcripts in 291 s, by hand; the Snowdon half needs the private model and the Ask transcript needs a key; `nrc-enrich-run` writes 2,438 values into 224 entities byte-exactly, but only under the tests' Run context; CI runs with `continue-on-error`. With this project: the Duplex half and `NrcWorkflows.Tests` run in CI on every push and assert the expected answers to the paper's eight questions; the Snowdon half runs on the owner's machine before each demo and its index names what was skipped; the write-back happens from a Run. Done: a push that changes one of the eight answers fails CI; the walkthrough index lists every figure or the reason it was skipped; the enriched IFC differs from the original only in the new property sets. Cost of failure: the paper's claims drift from the code and nobody notices until review.

## Principles

1. **One edit path.** Every gesture, MCP edit, and Ask turn is one of `addNode`, `connect`, `setParam`, `removeNode`, and a document written whole (`PUT`) is validated as if built from them: an agent's graph is one a person could have built, and no surface drifts from another.
2. **Nothing writes until Run.** Pure nodes memoize and re-evaluate freely; every writer lives in one pack and stays `EffectPending` until an explicit Run: evaluating for display can never touch a file, so exploration by a person or an agent is safe.
3. **Honest absence.** A missing measure stays missing: no NULL turned into 0, no size read from a name, no identity merged on a matching position; `InfoNotAvailable` is a deliverable: a fabricated complete answer misleads every decision downstream.
4. **Runs are the evidence.** A run pins the graph hash and every input by content hash and replays; a number an agent reports comes from a tool result, never from memory: that is the difference between a suggestion and evidence.
5. **Tables are the currency, and every wire can be peeked at.** Five value kinds travel on edges and almost everything is an immutable table; scalars are parameters edited on the node itself, never in a side panel, and a new type is a parameter kind, never a wire type: one vocabulary and one canvas serve ETL, SQL, 3D, charts, and checks, so a graph that computes a table colours the model in the same studio, and a new wire type touches the spec, the engine, every surface, and the conformance vectors.
6. **The catalog is the documentation; warn, never block.** Every node declares its ports, parameter kinds, enums, and purity, and `docs/nodes.md` is generated from that; live suggestions never reject a value, and an unknown column or an unparsable query is a warning with the parser's message, shown before any run: people wire graphs before the data exists, and agents ask instead of guessing.
7. **The agent works in the open graph.** Claude, in the Ask box or over MCP, knows which graph is open, what is selected, and the last result without being told an id; its edits land on that canvas selected and undoable, and its answers come from tool results: an assistant that has to be told what you are looking at is a second tool, not an integration. (Layering, one direction of dependency with a test that enforces it, stays a rule of `docs/ARCHITECTURE.md`; the build checks it, so it needs no place here.)
8. **The AI produces data, never verdicts.** A model may draft SQL, a graph, or a fact with provenance, always shown; a verdict is the deterministic execution of an approved rule, and approve, publish, and issue stay human verbs: a verdict a model invented cannot be replayed or defended, and the liability stays with a person. (unconfirmed)
9. **Start from data, not a blank canvas.** A new analysis opens from a model with a live table or from a template: a blank canvas asks people to know the vocabulary before they have a result. (unconfirmed)

## Replaces or augments

Replaces: SQL typed into a DuckDB shell and spreadsheet checks over exports; scripts against an authoring tool's API to get numbers out; screenshots and pasted tables as deliverables. Augments: DuckDB, Parquet, and Excel (BOS loads straight in, exports go straight out); Claude Code (two MCP servers and two skills); the IFC file itself, which stays the source of truth because write-back is byte-exact; web-ifc for parsing IFC and three.js for rendering.

## Scope

In: the BOS reference implementation with IFC loading, meshing, and byte-exact property-set editing; the specified dataflow engine (`deps/ara3d-dataflow`) and its conformance suite; the node packs, the headless host, the two MCP servers, the web editor and panes, the 3D viewer workspace and its pane inside the studio, so data graphs and 3D graphs are one graph over one host (TKT-28), and the publishing chain (report, dashboard, evidence package); samples that run without private data, and headless gates; Windows only for the full toolkit (the Revit add-in and the browser), while the engine and schema libraries are portable.
Out: authoring or editing geometry; a live connection to any authoring tool (the Revit add-in under `plugins/` exports a BOS file and is not extended in this stretch); a multi-user hosted service, accounts, or authentication; a second scripting API or an agent-as-code surface; several models in one graph or one Run (the `compare` report in `tools/building-model-workflows` stays as it is); clash detection beyond the `spatial.*` pack's bounding-box candidates; general node-graph instrument features no target workflow needs (semantic zoom, a canvas drawn in 3D, new wire types); porting the retired PoC or the alpha gallery wholesale, though single features are rebuilt from their design record; Gratify learning anything about BIM.
