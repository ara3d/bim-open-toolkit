BIM OpenToolkit

Open tools for getting tables, charts, checks, and 3D views out of building models without a vendor's API. A model is stored as plain tables (BIM Open Schema, or BOS), and questions about those tables become small graphs that people and AI agents build with the same four operations.

This page lists the repositories of the BIM Open family and their state on 2026-10-03, partway through splitting one repository, bim-open-toolkit, into several. The plan is docs/plans/repository-split.md.

The repositories

"Split out" means the code lives in that repository and the toolkit takes it through its deps/ folder. "Moving" means the repository exists but the code is still inside the toolkit, at the path given, until the phase named. None of the Pages sites below is published yet; each repository's owner switches Pages on in its settings.

BIM OpenToolkit

ara3d/bim-open-toolkit

The working repository and the analyst application: the studio host and its pages, the BIM node packs, the samples, the headless gates, and the NRC research work.

Hub. Still holds everything not yet split out. Phase 7 makes it the entry point a downstream project adds as one submodule, pinned to a tested tag.

BIM OpenFlow

ara3d/bim-open-flow

The graph system: node packs over tables, a headless host that evaluates graphs and records runs, the web editor, and an MCP server so an agent edits the same graph a person does.

Moving, phase 5. The code is in the toolkit's src/flow and bimopenflow/web; the repository holds a README.

BIM OpenNotebook

ara3d/bim-open-notebook

A record of a session with an agent as a document: each turn is a request in plain language and a reply whose tables, charts, and 3D views keep a snapshot and can be evaluated again.

Moving, phase 6. The code is in the toolkit's bimopenflow/web/packages/bim-open-notebook; the repository holds its first commit. It moves after TKT-86 cuts its imports from the editor's app package.

BIM OpenViewer

ara3d/bim-open-viewer

A WebGL viewer built on three.js, in 17 npm packages, that knows no file format: instanced drawing, per-instance colour, picking, section planes, and a model layer that tests run without a browser.

Split out, phase 2. main is at 35ce03b; the toolkit takes it as deps/bim-open-viewer, and both share one Gratify checkout.
Repository Pages site

BIM OpenData

ara3d/bim-open-data

The .NET implementation of BIM Open Schema and the IFC stack: reading and writing BOS files, IFC loading and meshing, byte-exact property-set editing, IFC to BOS and DuckDB, the IFC MCP server, and the BOS Browser.

Moving, phase 4. The code is in the toolkit's src/data, src/mcp/BimOpenMcp.Ifc, and apps/; the repository holds a README.
Repository Pages site

BIM Open Schema

ara3d/bim-open-schema

The specification: five dependency-free C# files that define the BOS tables (entities, parameters, relations, geometry) stored as Parquet. It contains no reader, writer, or converter.

Separate from the start. The toolkit takes it as the submodule submodules/bim-open-schema; BIM Open Data will take it through deps/.

How they depend on each other

The picture is the layout the split is heading for. An arrow points from a repository to one it builds on. The lower row holds general libraries that know nothing about buildings, except the schema.

How the pieces fit

A building model enters as an IFC file or as a BOS file exported from Revit. BIM Open Data reads it, converts IFC to BOS, and loads BOS into DuckDB, where every entity, parameter, and relation is a row. It also writes property-set changes back into the IFC file without touching any other byte.

BIM Open Flow turns a question about those tables into a graph of small nodes, each a pure function from tables to a table, a chart, or a 3D colouring. Nodes that write files wait for an explicit Run, and each run records the graph and its inputs by content hash so its numbers can be replayed. BIM Open Viewer draws the model in the browser, and a graph's output colours it. BIM Open Notebook keeps a conversation with an agent as a document whose answers are those graphs, tables, and views.

The toolkit joins them into the analyst application, with the node packs that know about buildings and the samples over real models. Each repository lists what it needs in deps.json and reads it only from its own deps/ folder, which node deps.mjs fills with a link to a sibling checkout or a clone at the pinned commit, so one checkout never holds two copies of a repository.
