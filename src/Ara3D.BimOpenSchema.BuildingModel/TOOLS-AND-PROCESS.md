# Tools, process and design approach

## What this version is

This project is the expanded **v0.1 review model**: authored C# definitions of recognizable building concepts, their relationships, workflow observations and analysis results. Its `.cs` files are authoritative for this version. XML comments explain what one row means, significant field meanings, units, uncertainty and accounting limitations.

The earlier `docs/proposals/bim-query-platform/contract/generated/BimDataModel.cs` remains a separate, older projection of the 23-table JSON contract. The new model expands beyond that contract. It is not generated by the earlier Python generator, and no round-trip synchronization between the two specifications is implemented. Editing the older JSON does not update these C# files.

The accompanying `model-coverage.csv` is a traceability and navigation index connecting definitions to users and workflows. It is not a generation source or an alternative definition of the record fields. Its existence does not establish that every workflow is implemented or that source data supplies every field.

## How the model is being developed

1. Start with users' decisions: room and finish schedules, trade takeoffs, panel and circuit coordination, procurement and receipt reconciliation, installation tracking, asset maintenance, performance reporting and audits.
2. Choose the useful row meaning. Distinguish an occurrence from a product definition, a material contribution, an observation and an analysis result. Add separate records when these have different identities or counting rules.
3. Make fields discoverable in domain records, using typed references for relationships. Share identity, evidence, geometry and units without requiring a large inheritance hierarchy.
4. State what incomplete inputs mean. A field can be unavailable because it was not observed, was not exported, is inapplicable, is invalid or conflicts with other observations. These states do not mean zero, false or physical absence.
5. Exercise representative records and cross-record cases in the accompanying tests. Correct the design when constructing realistic examples exposes missing scope, units, relationships or uncertainty.
6. Review the C# and coverage index together. A proposed field should answer a recognizable question; a plausible concept alone is not sufficient reason to introduce another class.

Delegation used explicit file ownership: architectural/place definitions, building services, and commercial/operational definitions were developed independently, with shared names coordinated centrally. The main agent owns integration, the project boundary, the shared value types, documentation navigation and final build/test verification. Subagent reviews checked incomplete totals, graph completeness, spatial candidate claims and terminology across those boundaries.

## Data sources and what a record does not imply

The model distinguishes four kinds of information:

| Information | Examples | Interpretation |
|---|---|---|
| Building data | Spaces, walls, fixtures, geometry, materials | May be mapped from BOS when available; defining a field does not prove an exporter supplies it. |
| Workflow observations | Deliveries, installation progress, inspections, maintenance | Usually supplied by operational tools or people and related to building identities. |
| Versioned external information | Rates, requirements, environmental factors | Requires identifiable authority, version and applicability; it cannot be inferred from geometry. |
| Computed or assessed results | Estimates, impacts, service traces, conflicts, egress findings | Retains method, scenario and input coverage; a result record is not an implemented calculation engine. |

Revit-created BOS samples are the more reliable reference collection identified by the user. The incomplete IFC-to-BOS converter can omit data. Missing exported topology, for example, cannot prove a physical network is disconnected. Source mappings, exporter coverage and spatial interpretation require separate validation against actual files.

## Platonic.CSharp integration

`Ara3D.BimOpenSchema.BuildingModel.csproj` directly imports `../../tools/bim-data-model/Platonic.props`. That shared configuration references `Platonic.Core` and `Platonic.Analyzers`, defaulting to version `0.1.0`. When present, the sibling `C:/Users/cdigg/git/Platonic.CSharp/artifacts` directory is added as a package source. `PlatonicRoot` and `PlatonicVersion` remain configurable MSBuild properties.

The import enables nullable reference checking, the current configured C# language version and warnings as errors, with the shared package-advisory exceptions. The model uses sealed immutable records, readonly value types and immutable collections. Its definitions and checks remain in the pure model boundary. Test infrastructure that performs reflection, file access or other effects belongs behind the test project's explicit `Impure` boundary; that does not exempt production model code from the analyzers.

`ModelChecks.cs` returns immutable findings for selected consistency rules. Examples include a complete estimate hiding unpriced scope, a bounds candidate claiming solid overlap volume, and a pass reported with incomplete relevant evidence. These checks do not implement full referential integrity, financial calculations, geometric predicates or regulatory compliance.

## Tools and verification responsibilities

Repository inspection uses PowerShell and `rg`; file changes use the workspace editing tools. The .NET SDK restores and compiles the model and runs its integration tests. XML documentation generation makes the comments available to C# tooling as well as source readers. No new database, graph-query engine or code-generation dependency is required by this project.

Build and test execution is centralized to avoid competing writes to shared build outputs. Final results belong in the main agent's verification report and retained test output. This process document does not assert a test count, successful build, validated BOS mapping or achieved performance measurement.

## Scale and remaining architectural work

These C# records describe meaning and support bounded query results and review examples. They are **not** an allocation plan for hydrating millions of heap objects. In particular, `Fact<T>`, evidence collections and relationship collections must not be interpreted as a requirement to eagerly materialize an entire building portfolio.

BFAST preparation, columnar storage, database projections, indexing, selective loading and source conversion remain separate architectural work. Prepared opening plus the first useful query still targets ten seconds, with a 16 GiB process-memory baseline on a 32 GiB workstation. Defining or compiling these records does not demonstrate either target.

The next integration decisions include which domain fields can be mapped reliably from each exporter, which workflow records need external inputs, which projections deserve persisted tables, and whether a compact shared catalog should eventually generate both C# and database/schema artifacts. Until that generation path exists, this authored model and the older JSON prototype must be reviewed as separate versions.
