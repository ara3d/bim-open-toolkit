# Builder brief: STEP mesher complexity chunks

Read this whole file, then `docs/plans/step-mesher-complexity.md` (the plan: ranked candidates, the testing strategy, the chunk table), then `sandbox/step-mesh-staging/README.md` (the staging rules), then your ticket. You build one chunk of the plan, in your own staging folder, and stop when it is green and committed. The supervisor merges it.

## Your chunk

The dispatch message names your chunk id (for example `F1`), its ticket (`TKT-nnn`), and your staging folder `sandbox/step-mesh-staging/perf-<name>/`. The plan's chunk table row is the specification: the functions to add, the candidates it fixes (read their rows in the ranked table, each quotes the line that makes the cost what it is), the laws that must keep their verdicts, and the count witness. The ticket's acceptance criteria are the definition of done.

## How to work

1. Read the function you are fixing and every caller (grep; the plato-navigation MCP server indexes only the Plato stdlib, not this library). Read `sandbox/step-brep-mesh/PLATO-PRIMER.md` for the language, `VOCABULARY.md` for the layer order (a layer references only lower layers), and the layer's `README.md`.
2. Write new files only, in your folder: the replacement body under a new name (`<Name>Body` for a bodiless function, a renamed replacement such as `UnwrapIndexed` for one that has a body), its counted form `<Name>Counted(...): Counted<X>` where the chunk asks for a count witness, laws named `Law_Perf_*`, and `TRACK.md` (template in the staging README) with the one-line wiring edits the supervisor makes at merge under "Merge instructions". Never edit a file under `sandbox/step-brep-mesh`. Do not touch `sandbox/step-mesh-staging/prepare` or any other staging folder.
3. Keep results bit-identical where the plan says so (a table, a bound value, an index change the same arithmetic). Where a fix changes a floating-point result (a seeded search, an early stop), say so in `TRACK.md` under "Findings" and show the verdicts before and after.
4. Check on the warm server: `python -I sandbox/step-brep-mesh/tools/plato_laws.py "<laws>" --staging sandbox/step-mesh-staging/perf-<name> --budget 20`. "0 laws, 0 type errors" means a file did not parse: run the pinned CLI below without `--backend=csharp` to see which. A type error names the file and line.
5. Once green, run your chunk's laws on the compiled backend, from `C:/Users/cdigg/git/plato`:
   `dotnet C:/Users/cdigg/.plato-cli/e37c032f/Plato.CLI.dll run stdlib/foundation stdlib/geometry stdlib/graphics C:/Users/cdigg/git/bim-open-toolkit/sandbox/step-brep-mesh C:/Users/cdigg/git/bim-open-toolkit/sandbox/step-mesh-staging/perf-<name> --recursive --exclude=brep.types.plato --exclude=brep.library.plato --exclude=brep.concepts.plato --laws --backend=csharp --profile=cpu64 --budget=2 --filter=<comma list of laws or law blocks>`
   (about 35 s before the laws run). A law over 2 s compiled is a defect in your chunk; fix it or split the witness family, never loosen the law. Record the compiled line in `TRACK.md`.
6. Commit by path, only your folder and your ticket: `git add sandbox/step-mesh-staging/perf-<name>` then `git commit -m "<message>" -- sandbox/step-mesh-staging/perf-<name> tickets/TKT-nnn-*.md`, with trailers `Ticket: TKT-nnn` and `Agent: builder <your CLAUDE_CODE_SESSION_ID>` and the Co-Authored-By line the environment gives you; push. Set `Status: ready: <chunk id>` in `TRACK.md` in that commit. Tick the ticket's boxes you met. If the commit guard says another session has edits in a file, you touched a file outside your fence: revert that file.
7. Report (your final message): what you built (functions and types added, with the one-line wiring), the laws run with counts and verdicts on both backends, the count witness's slope and sizes and the measured work at each, findings, and a duration per step (reading, writing, law runs, compiled runs, waiting).

## The testing strategy, binding

Every test is a law under 2 s compiled. No wall-time test. Three kinds, all three in your chunk where the row asks:

- **Shared witnesses.** A witness that holds a mesh, discretization or triangulation is a `Witness_*` value the runner builds once per sweep, never a function a law calls per case. Chunks L1, L3, L4 add `MeshedWitness`, `DiscretizedWitness`, `TriangulatedWitness`; until they merge, a law that needs a built value binds it once in a block body (`var t = ...;`) and tests several claims on it.
- **The count witness.** Your `Witness_<Family>Work(_: WorkClaim): WorkClaim` names the family, the slope (`Flips(1)`, `Evaluations(2)`, `Insertions(3).Add(Flips(1))`, ...), two or more growing sizes, and `n => <work at n>`, a function that builds the family at size n and reads `<Name>Counted(...).Work`. The one law `Law_WorkIsWithinSlope` (layer 00) is its test; add no law for it. Pick sizes that show growth (32 and 128, or 8 and 64), with the larger one still well under 2 s compiled. What a count counts: `Evaluations` for surface and curve evaluations and projections the function makes itself, `Insertions` for array elements copied or candidates visited, `Flips` for flips or table rebuilds. The witness's comment says which, and the slope is what the fixed function needs, not what the old one did. Build `Counted` with its constructor `Counted(value, work)`: a generic helper function is not monomorphized by the C# writer. A function-typed field is projected alone (`c.WorkAt`) and applied through a function-typed parameter, never called as `c.WorkAt(n)`.
- **Verdict preservation.** The laws in your row's test column keep their verdicts against `sandbox/step-brep-mesh/reviews/verdicts-cpu64.tsv` (grep the law there). Your replacement is not wired into the library until merge, so to show preservation stage a law `Law_Perf_<Name>Agrees` that the replacement equals the original on the witnesses the original's laws use (same value, or same up to the tolerance the plan allows), and run the original's laws unchanged.

Plato facts that cost earlier builders time: `&&`, `||`, `All`, `Any` evaluate every operand; `n.Range` and `MapRange` allocate; `Take`, `Concatenate`, `Append`, `Skip` copy; a `List` or `Buffer` builder cannot be a function's first parameter, stored in a record, or captured by a lambda (primer A.6), so a pass that builds in a list inlines its loop; a `match` on a local `var` fails at run time, match on a parameter or a call; the first parameter of a library function must be a concrete type or interface, never a type variable; a sum case and a function of the same name collide in C#; a field named `At` collides with the indexer.

## Stop and report when

- the chunk needs a change to a type or signature the library already has: write it under "Contract requests" in `TRACK.md`, build what you can without it, and say so in your report;
- the same check has failed after three different fixes, or the only way forward loosens a law;
- the chunk is larger than two hours: commit the green part, say what remains.
