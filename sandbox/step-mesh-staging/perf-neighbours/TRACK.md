## Findings
- Bit-identical: a pass sets triangles in place or appends them (`WithTriangles`) and never removes or reorders one, so a carried slot index names the same side in the next pass; every table a step reads equals the one `NeighbourSlots` would have built (`Law_Perf_CarriedTableIsNeighbourSlots`, both backends, all 42 faces, every round), and the steps are otherwise the library's code, so the trials, insertions and marks are the same. `Law_Perf_RefineCarriedAgrees` confirms the result field for field.
- TKT-355's `Law_UpdatedNeighboursAreTheTable` at k = -1 does not reproduce and is not the table's. `TriSampleModel(-1)` is `((-1 % 6) + 6) % 6 = 5`, `Witness_Box(2, 3, 4)`, both today and at d3d297ce (`TriWitnessIndices` was `[0, 1, 5, 6, 8]` then too); the ticket's "sphere by pole loops (index 9)" misnames the model. A probe law restoring the integer form, `EveryTriangulableFace(k, (m, f, r, chart) => m.UpdatedTableIsTable(f, r, chart))`, passed 14 cases exhaustive on the interpreter and on the compiled C# with Plato e37c032f, and the witness form `TriangulatedWitnessLaws.Law_UpdatedNeighboursAreTheTable` (which covers the box's six faces) passes on both. Whatever differed at d3d297ce is gone from the current library; no expression differs today.
- The warm server (`tools/plato_laws.py`) answered "0 laws" for every filter from 19:49 to 19:50, including `RefinementTestCachedLaws` with no staging folder, while the pinned CLI parsed the same tree; it is down for everyone, not a parse error of this folder.
